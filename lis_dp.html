1The Problem

Longest Increasing Subsequence (LeetCode #300)

Given an array of integers, return the length of the longest strictly increasing subsequence.

Before solving anything, we need to read that sentence the same way. Four questions, each with a tiny example.

What is the input?

One list of numbers, which we will always call numbers. The order they arrive in is fixed and we may never change it.

What is a subsequence?

Any set of elements read left to right, where we may skip but never reorder.

Pulled from numbers = [5, 6, 1, 2, 3]Legal?Why
1 → 2 → 3yeswe skipped two elements and kept the survivors in their original order
5 → 6yeswe skipped everything after them
1 → 3 → 2nothe VALUE 2 sits before the VALUE 3 in the array, so this is a reorder, not a skip
5 → 5nothere is only one 5 and we cannot reuse an element

What does "strictly increasing" forbid?

Every next element must be bigger than the one before it. Equal is not enough. In [2, 2, 2] the longest strictly increasing subsequence has LENGTH 1, not 3.

What do we return?

A LENGTH. One number, counting elements. We are not asked for the chain itself.

Say the answer out loud before solving: "the function returns how many elements are in the longest rising chain we can pull out of numbers." Every number we produce from here on gets checked against that sentence.

Three things people mix up: the input array, the chain we pull out, and the LENGTH we return.

So next: we know what is being asked. What would someone with no DP training actually try?

2What Would I Try First?

We already know: we must return the LENGTH of the longest rising chain in [5, 6, 1, 2, 3].
The natural try: walk left to right. Keep a running chain. Take the current number if it is bigger than the last number taken. Otherwise skip it.

It feels safe because it never breaks a rule. Everything it takes really is bigger than the previous pick, so whatever it builds is a valid increasing chain. Let us run it.

3Exactly Where It Fails

The true answer is LENGTH 3, so this is not a small inaccuracy, the method is wrong. But wrong where? Pointing at the exact step is the whole reason this section exists.

the chain greedy never found: 1 → 2 → 3, LENGTH 3

The failure happened at step 2, when we took the VALUE 6 at current_index = 1.

Taking it looked free. It cost nothing and made the chain longer immediately, from LENGTH 1 to LENGTH 2. But it raised the bar every future element had to clear, from "bigger than 5" to "bigger than 6". The entire rest of the array sits below that bar. One cheap gain at step 2 destroyed a chain of LENGTH 3 that had not started yet.

The mistake is not where greedy gets stuck. It is at step 2, where greedy got greedy.

The blocking realisation: a decision at current_index = 1 changes what is legal at current_index = 4. We cannot judge a decision by what it earns now, because its real cost appears later. So we cannot commit to one future without checking the others.
Would greedy work if we just started the chain from a later element instead?
No, so patching the starting point does not save the method. Forced to start at the VALUE 1, greedy would find 1 → 2 → 3 and get lucky here. But on numbers = [1, 100, 2, 3, 4] a greedy walk still grabs the 100 and stalls at LENGTH 2, while the truth is 1 → 2 → 3 → 4, LENGTH 4. The flaw is committing to a take without seeing its later cost, and that survives any choice of starting point.
So next: if we cannot safely commit, we must slow down and name the decision we are stuck on.

4What Am I Stuck Deciding?

We already know: an early take can silently kill a longer chain, so no forward-looking rule is safe.

Instead of the huge question ("what is the longest chain in the whole array?"), we ask a narrower one we might actually be able to answer:

"What is the longest chain that ends on this element?"

Why is that a good question to get stuck on? Because a chain ending here is almost fully determined. The last element is pinned. The only unknown is what sits immediately before it.

Whatever sits immediately before must be smaller in VALUE and earlier in INDEX. Exactly two candidates qualify, plus one possibility that is easy to forget: maybe nothing comes before, and the chain is the single element by itself.

The uncertainty, stated precisely: three different chains could end here. Which is longest? We cannot tell by looking. We would need to know the LENGTH of the chain ending at current_index = 2, and the LENGTH of the chain ending at current_index = 3. Those are questions of exactly the same shape as the one we are stuck on.

The decision is not "take it or skip it". It is "which earlier chain do I attach to?"

Notice what happened. While describing why we were stuck, we produced smaller copies of the same question. That is the signal recursion is about to be useful.

So next: we need something that answers "how long is the chain ending at that index?" without us solving it by hand.

5The Recursion Promise

We already know: to answer about current_index = 4 we need answers about current_index = 2 and 3.

Recursion is usually taught as "a function that calls itself", which is true and useless. Here is the usable version:

The promise: if I hand the function a smaller version of the same question, it hands back the correct answer to that smaller question. I do not need to know how it got there. I only need to know what the answer means, so I can use it.
longest_chain_ending_at(current_index = 4)
longest chain ending on numbers[4] = 3
↓  asks: "how long is the chain ending at INDEX 3?"
longest_chain_ending_at(current_index = 3)
longest chain ending on numbers[3] = 2
↑  returns LENGTH 2, meaning the chain 1 → 2
longest_chain_ending_at(current_index = 4)
now it can finish: 1 → 2 plus its own element

One question this always raises, so let us answer it now: if every call needs a smaller call, when does it stop?

Every call points at a strictly smaller INDEX. INDEX 4 asks INDEX 3, INDEX 3 asks INDEX 2, and INDEX 2 has nothing smaller to its left, so it answers directly. The ladder has a floor.

Does longest_chain_ending_at(3) need to know who called it?
No, and that is the point of the promise. It answers one fixed question, "how long is the longest chain ending on numbers[3]?", and the answer is LENGTH 2 no matter who asked. The caller decides what to do with the number. If a call ever needed to know its caller, the question would not be self contained and recursion would not work here.
So next: before drawing anything, pin down exactly what one call returns.

6What Does One Call Mean?

We already know: a smaller call promises a correct answer, and every call points at a smaller INDEX.

This is the most important definition on the page. If it stays fuzzy, the base case, the +1, the strip and the final answer all become guesswork.

Notice current_index = 1 returns LENGTH 2, which is bigger than what current_index = 2 returns, even though INDEX 2 is further right. The returned LENGTH has nothing to do with how far along we are. It describes only the chain ending at that one spot.

What does longest_chain_ending_at(2) return, and why is it not 3?
It returns LENGTH 1. INDEX 2 holds VALUE 1. For a chain to end there, the element before it must be earlier and smaller than 1. The only earlier values are 5 and 6, both bigger. So the longest chain ending there is the single element, LENGTH 1. It is not 3 because three elements have been passed, and passing is not using. The promise counts chain links, not array positions. This is exactly the INDEX versus LENGTH confusion the contract block above is built to prevent.
So next: with one call clear, follow a single call down and watch the answer come back.

7Down to the Floor, and Back Up

We already know: one call returns the LENGTH of the chain ending at one INDEX.

We are deliberately not drawing a recursion tree. A tree shows many things at once and is unreadable until you can read one path. So: one narrow path, all the way down, then all the way back.

Going down: asking smaller questions

BASE CASE nothing to the left is smaller, so nothing to delegate

Each step is smaller in two ways at once. The INDEX shrinks, and the number of candidates shrinks with it. That is what guarantees we land.

Reaching the base case, and why the answer is 1

At INDEX 2 the VALUE is 1. To extend a chain onto it we would need an earlier element smaller than 1. Looking left we find 5 and 6, both bigger. There is no smaller question to ask, so we answer directly.

The answer is LENGTH 1, not 0. The chain consisting of just that element is a perfectly valid strictly increasing chain with one element in it. Returning 0 would claim no chain ends there at all, which is false. Every single element is always a chain of LENGTH 1, and that fact is the floor the whole recursion rests on.

Trace one number through. The 3 at the top is 1 + 2. That 2 is not from the array, it is what the call below returned. And that 2 is 1 + 1, where the inner 1 is what the base case handed up. So the final 3 is literally the base case's answer, transformed twice on the way up.

At current_index = 3 the sum is 1 + 1. There is a VALUE 2 sitting right there. Why is it not 1 + 2?
The visible 2 is a VALUE and VALUEs never enter this arithmetic. The two ones mean different things: the first is one element, our own numbers[3] being appended, and the second is a returned LENGTH, how many elements were in the chain ending at INDEX 2. We are counting links in a chain, not adding up the numbers inside it. This is why every term in the boxes above carries a caption saying what it counts.
So next: INDEX 3 was only one option. What were the others?

8Discover All Legal Choices

We already know: attaching to INDEX 3 produced a chain of LENGTH 3.

Standing at current_index = 4, the question "which earlier chain do I attach to?" has one candidate per earlier index, plus the option of attaching to nothing. Test all of them rather than assume.

previous_indexVALUE theresmaller than 3?Result
05noillegal, 5 cannot sit before 3 in a rising chain

start freshnonealwayslegal. the chain is the single element = LENGTH 1

Five candidates, three legal futures, returning LENGTH 2, 3 and 1.

Why these are the only choices

Listing branches is not enough. We must argue nothing valid escapes them, or we could be quietly losing the answer the way greedy did.

The argument is short. Take any valid chain ending on numbers[4]. There are only two possibilities:

  • It has some element immediately before. That element sits at some previous_index < 4 and must be smaller in VALUE. We tested every index below 4, so it was covered.
  • It has nothing before. Then it is the single element, which is exactly the start fresh branch.
No chain ending at INDEX 4 escapes these branches. Every chain either has a predecessor (covered by the loop over all earlier indices) or does not (covered by starting at LENGTH 1).
Tempting extra branchWhy it is not needed
"skip the current element"Handled, but not here. Skipping means the answer chain ends somewhere else, and that case is covered by calling the function on that other index. Our promise says the element is always included, so "skip" is not this function's job.
"attach to the closest smaller element"That is greedy again. Here the closest smaller element happens to be right, but nothing guarantees it. That is a guess, not a branch.
"attach to two earlier elements at once"A chain has exactly one element immediately before the last. The rest is already counted inside the returned LENGTH.
Without the start fresh branch, what would the code return for numbers = [9, 8, 7]?
Zero, which is wrong. In [9, 8, 7] no element has a smaller element to its left, so no legal previous_index is ever found and there is nothing to take a max over. The correct answer is LENGTH 1, since any single element is a chain. This is why start fresh is not an optional extra: it is the base case in disguise, and it is why we initialise longest_so_far to 1 rather than 0.
So next: before combining those three numbers, work out what information a call actually needs.

9Discover the Bookmark

We already know: a call tries every legal earlier index, plus starting fresh.

Suppose we stop halfway and hand the work to someone else, leaving them a single note. What has to be on that note for them to finish without asking us anything?

The test for each candidate is the same: if two situations differ only in this, can the remaining answer differ? If no, it does not belong on the note.

10Derive the Operator

We already know: at INDEX 4 the legal branches returned LENGTH 2, 3 and 1.

We have three numbers and must produce one. Nothing in the code tells us which operation. The wording of the question does.

Why max

Each branch produced a real, legal chain ending on our element:

Why +1

Ask a narrower question: what did this branch accomplish immediately, before any delegation?

It placed exactly one element on the end of a chain the smaller call already built. One element joined, so the count rises by exactly one.

max comes from the word "longest". The +1 comes from placing exactly one element.

The +1 counts an ELEMENT, never a VALUE. At INDEX 4 the VALUE is 3 and it is tempting to write +3. But we count how many elements are in the chain, not their sum. On numbers = [1, 9] the answer is LENGTH 2, not 10. Had the problem asked for the largest sum of an increasing subsequence, then and only then would the VALUE be added instead of 1.
If the problem asked "how many different longest increasing subsequences are there?", which of max and +1 would change?
Both, differently. Counting chains means branches no longer compete, they accumulate, so max becomes a sum over the branches that tie for the best LENGTH. And +1 leaves the counting arithmetic entirely, because appending an element extends a chain rather than creating an extra one. You would track two numbers per index, a best LENGTH and a COUNT of chains reaching it. Same story shape, different operators, which is the whole reason we derive operators instead of memorising them.

11Write the Recurrence

We already know: every branch, every transition, and both operators.

Only now is it safe to write the formula, because it introduces nothing new. It is shorthand for the last four sections.

longest_chain_ending_at(current_index) = max(
    1,
    max over every previous_index < current_index
        where numbers[previous_index] < numbers[current_index]
        of  1 + longest_chain_ending_at(previous_index)
)

answer = max over every current_index of longest_chain_ending_at(current_index)
PieceWhich section it came from

That last line is not decoration. The function only ever answers about one ending point. The problem never said where the chain ends, so we ask at every possible ending and keep the best. Forgetting this line is the most common way to get LIS almost right.

13Marked Code Walkthrough

We already know: every line below corresponds to something we derived by hand.
# Returns the LENGTH of the longest strictly increasing chain
# whose last element is numbers[current_index].
def longest_chain_ending_at(current_index):
    longest_so_far = 1
    for previous_index in range(current_index):
        if numbers[previous_index] < numbers[current_index]:
            longest_so_far = max(longest_so_far,
                                 1 + longest_chain_ending_at(previous_index))   # RECURSION HAPPENS HERE
    return longest_so_far


answer = max(longest_chain_ending_at(current_index)
             for current_index in range(len(numbers)))
def longest_chain_ending_at(current_index): The bookmark becomes the parameter. One INDEX in, one LENGTH out. Nothing else is remembered between calls, which is exactly what section 9 argued for. The name says what it returns, so you never have to remember what it does.
longest_so_far = 1 This one line is the start fresh branch and the base case at once. It asserts that a chain of just our own element always exists. If no legal predecessor is ever found, the loop body never runs and this 1 is what gets returned. Delete it and [9, 8, 7] returns 0.
for previous_index in range(current_index): Try every earlier index as the element immediately before ours. Not the nearest, not the first that works, all of them. This exhaustive sweep is precisely what greedy refused to do, and it is why we no longer lose the answer.
if numbers[previous_index] < numbers[current_index]: The legality test, enforcing "strictly increasing". Change it to <= and [2, 2, 2] starts reporting 3. Note the loop ranges over INDEXes while this line compares VALUEs. Both conditions are needed: earlier in position, and smaller in value.
longest_so_far = max(longest_so_far, 1 + longest_chain_ending_at(previous_index)) Three derived ideas on one line. The inner call is the delegation, returning a LENGTH. The 1 + pays for appending our own element. The max keeps this branch only if it beats everything tried so far. Note that numbers[current_index] never enters the arithmetic, only the count does.
return longest_so_far The promise, kept. What we hand back must be "the LENGTH of the longest chain ending exactly here", and it is: we started at 1 and only ever replaced it with a longer legal chain that also ends here.
answer = max(longest_chain_ending_at(current_index) for current_index in range(len(numbers))) Outside the function. The chain must end somewhere and nobody told us where, so ask at every index and keep the best. This line is not optional and it is not the value at the last index.
Read the recursive line aloud "Take the LENGTH of the best chain ending at the earlier index, add one for my own element, and keep that only if it beats the best I have found so far."

Six lines, six ideas, all derived before they were written.

The real test: if this code were deleted, sections 4 through 12 would let you write it back. That is the difference between understanding a solution and having seen one.
Which single line stops this from looping forever?
The orange line, for previous_index in range(current_index). Because previous_index is always strictly less than current_index, every recursive call moves to a smaller INDEX, and indices cannot go below 0, so the chain of calls must terminate. If it were range(len(numbers)) a call could delegate to itself or to a larger index and recurse forever. The legality test does not save us there, since it constrains VALUEs, not direction.
So next: run it on the whole array and account for every number it produces.

Do not read the wrong cell. On this array the last cell happens to hold the answer, which makes return longest_chain_ending_at[-1] very easy to write and pass. On numbers = [1, 2, 3, 1] the returned lengths are 1, 2, 3, 1, the last is LENGTH 1, and the answer is LENGTH 3. Always take the max.
Why does current_index = 2 return LENGTH 1 when two elements sit to its left?
Because both of them, VALUEs 5 and 6, are larger than the VALUE 1 at INDEX 2. So next: look carefully at that trace. One question was answered more than once.

15What Is Calculated Again?

We already know: every call returns a LENGTH, and the answer is the max over all of them.

Saying "there are overlapping subproblems" explains nothing. Let us find the exact repeat and name it.

Follow the calls made while computing longest_chain_ending_at(4). Two different routes reach the same place:

RouteThe path takenWhy it goes there
AINDEX 4 → INDEX 2VALUE 1 is smaller than VALUE 3, so it is a legal predecessor
BINDEX 4 → INDEX 3 → INDEX 2VALUE 2 precedes VALUE 3, and VALUE 1 precedes VALUE 2
OccurrenceStateThe question, in EnglishAlready solved?
1stcurrent_index = 2longest chain ending on the VALUE 1no, compute it
2ndcurrent_index = 2longest chain ending on the VALUE 1yes, identical question

Two different histories, one identical remaining question.

Be precise about the waste. It is not that the number 1 appears twice, numbers repeat harmlessly all the time. It is that the program re-derives the answer to the same question. The second time, it rescans the earlier indices, retests both comparisons, and rebuilds a conclusion it already reached.

And that is only inside one subtree. Across the whole top level loop, current_index = 2 is reached four separate times: once when the top level asks about index 2 itself, once inside the call for index 3, and twice more inside the call for index 4 (directly, and again by way of index 3). On a strictly increasing array this compounds and the call count grows exponentially.

On [1, 2, 3, ..., 20]: twenty distinct questions, 1,048,575 calls. That gap is the entire justification for what comes next.
So next: the fix is embarrassingly direct. Write the answer down the first time.

16Memoization

We already know: the same index was asked and answered more than once, identically.

Memoization is one sentence: before solving a bookmark, check whether we already answered it.

Both pieces follow from what we built. The key is the state, which section 9 established is just current_index. The value is whatever the function would have returned, which section 6 established is a LENGTH.

The complexity collapses. There are n distinct states, each doing a scan of at most n earlier indices, so we go from exponential to O(n2) time and O(n) space.

Why is the cache keyed only by current_index, with nothing about the chain built so far?
Because the chain built so far cannot change the answer. The call for INDEX 2 means "longest chain ending on the VALUE 1", and that is LENGTH 1 regardless of who asked or what they had collected. Section 9 tested this candidate and dropped it. If the answer did depend on the caller's history, the index alone would not identify the question, the cache would return wrong answers, and we would have chosen the state incorrectly. A cache key that is too small is not a caching bug, it is a state bug.
So next: if every index is solved exactly once anyway, why make calls at all?

17Recursion Becomes a Table

We already know: each index is solved exactly once and stored under that index.

Look at what the cache became: a set of slots, one per index, each holding a LENGTH. That is an array. And an array indexed by position is a table.

So we keep the name. The only thing that changes is the brackets:

longest_chain_ending_at(2) becomes longest_chain_ending_at[2]

Same name, same question, same answer. Round brackets ask for it, square brackets look it up.

A call, a cache entry and a cell are three containers for one identical fact.

So what actually differs? Only the order answers get produced. Recursion asks for an answer the moment it needs it, and if the answer does not exist yet it goes and computes it. A table flips this: fill cells in an order where every cell a formula needs is already filled. Then no asking is required, only reading.

What order works? Section 9 already told us. The bookmark always moves left. So filling left to right means everything we need is behind us and done.

So next: fill the strip and read every cell out loud.

Why the fill order works

Cell current_index only reads cells at smaller indices. When we arrive, every one of those is already finalised. No cell needs a value from its right, so a single left to right pass is enough. If a dependency ever pointed the other way, this order would read an unfinished cell and produce nonsense.

def length_of_lis(numbers):
    if not numbers:
        return 0

    # longest_chain_ending_at[k] = LENGTH of the longest chain ending at index k
    longest_chain_ending_at = [1] * len(numbers)

    for current_index in range(len(numbers)):
        for previous_index in range(current_index):
            if numbers[previous_index] < numbers[current_index]:
                longest_chain_ending_at[current_index] = max(
                    longest_chain_ending_at[current_index],
                    1 + longest_chain_ending_at[previous_index])

    return max(longest_chain_ending_at)

No recursion, no cache, no stack depth. Same five answers, produced in an order that guarantees they are ready. O(n2) time, O(n) space.

Could we fill the strip right to left instead?
Not with this state definition. Each cell reads cells to its left, so going right to left would read cells not yet computed, all still holding their initial 1. On our example cell [4] would compute 1 + 1 = 2 from an untouched [3] and we would report LENGTH 2 instead of 3. You can build a right to left version, but only by redefining the state as "longest chain starting at this index", which flips every dependency. Fill order is not a style choice, it is dictated by which way the state moves.
So next: the usual final step is to shrink the table. Let us check whether we can.

19Space Optimization

We already know: each cell reads cells to its left, and we fill left to right.

The usual move is to notice only a couple of recent cells are ever read and collapse the array into a few variables. Let us check whether that applies rather than assume.

The question is: which earlier cells does a cell actually read?

ProblemA cell readsCan we compress?
Climbing Stairs / House Robberonly the previous two cellsyes, keep 2 variables, O(1)
Longest Increasing Subsequencepotentially every earlier cellno, keep all n

The inner loop is for previous_index in range(current_index), with no bound on how far back a legal predecessor sits. On numbers = [1, 100, 101, 102, 2] the last cell's only legal predecessor is INDEX 0, the very first cell. Throw it away and the answer is lost.

The honest conclusion: O(n) space is already the answer. Not every DP compresses, and being able to say why is worth more than forcing an optimisation that does not exist. The dependency window here is the entire prefix, so every cell stays.

What is worth improving is the time, not the memory. There is an O(n log n) solution that abandons the "ending at" state entirely and tracks something different, the smallest possible tail value for a chain of each length, maintained with binary search. It is a genuinely separate derivation with its own story, and bolting it on here would break the one we have been telling. Worth knowing it exists. Worth deriving separately, not memorising.

So next: the specific ways this solution gets broken.

The trigger to remember

When I see "keep the order, skipping is allowed, find the longest", I define the state as "the best answer ending at this index", scan every earlier index as a candidate predecessor, and take the max over all endings at the end.

Anchoring the state by where something ends is the transferable idea. It reappears in maximum sum increasing subsequence, longest chain of pairs, Russian doll envelopes (sort first, then it is literally this), and longest arithmetic subsequence. Anchoring at the end is what turns "what came before?" into a question with a finite, checkable list of answers.

Rediscover it later

Six months from now the recurrence will be gone. The story is what has to survive, so here it is with no code in it:

2I froze on one element and asked a narrower question: what is the longest chain that ends here?
3To answer it I needed the chain length ending at each smaller earlier element, which is the same question again. So I let recursion promise me those.
