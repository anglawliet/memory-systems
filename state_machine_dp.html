The Problem

Best Time to Buy and Sell Stock with Cooldown (LeetCode #309)

You have stock prices for each day. You can buy, sell, or rest. After selling, you must wait one day (cooldown) before buying again. Maximize profit.

prices = [1, 2, 3, 0, 2]

Best strategy: buy day 0 ($1), sell day 2 ($3), cooldown day 3, buy day 3 ($0), sell day 4 ($2). Profit = (3-1) + (2-0) = $3.

Why is this different? You can't just "grab or skip" like knapsack. Your available choices depend on what state you're in. Holding a stock? You can sell or keep holding. Just sold? You must rest. Resting? You can buy or keep resting.

Step 1: What Are My States?

Three states, five transitions

HOLD
I own a stock. I can:
Keep holding (stay in HOLD)
Sell today (move to SOLD)
SOLD
I just sold. I must:
Cool down (move to REST)
No choice, mandatory.
REST
I'm free to act. I can:
Buy today (move to HOLD)
Keep resting (stay in REST) 
Transitions:
  HOLD  ->  HOLD   (keep holding)
  HOLD  ->  SOLD   (sell: + price)
  SOLD  ->  REST   (mandatory cooldown)
  REST  ->  HOLD   (buy: - price)
  REST  ->  REST   (keep resting)
The constraint creates the states. "Cooldown after selling" means selling and resting are different states. Without cooldown, you'd only need HOLD and REST.

Why each variable changes

State: max_profit(day, state). Two state variables: which day, and which state we're in (rest, hold, or sold).

FROM REST: Two choices
BUY (rest → hold)
Action: Buy stock at today's price.
Immediate cost: -prices[day]. Money spent to buy the stock.
State changes:
day → day+1: This day is done. Move to next day.
state: rest → hold: We now own a stock.
Call: -prices[day] + max_profit(day+1, "hold")
Why does state change? Buying means we now hold a stock. Our future choices are different (sell or keep).
WAIT (rest → rest)
Action: Do nothing. Stay resting.
Immediate cost: +0. No transaction.
State changes:
day → day+1: This day is done. Move to next day.
state stays rest: We didn't act. Still free to buy or wait tomorrow.
Call: max_profit(day+1, "rest")
Decision: max(buy, wait).
FROM HOLD: Two choices
SELL (hold → sold)
Action: Sell the stock at today's price.
Immediate reward: +prices[day]. Money received from selling.
State changes:
day → day+1: This day is done.
state: hold → sold: We just sold. Must cooldown next.
Call: prices[day] + max_profit(day+1, "sold")
Why sold, not rest? The cooldown rule: after selling, you must wait one day. The "sold" state enforces that constraint.
KEEP HOLDING (hold → hold)
Action: Don't sell. Keep the stock for a better price later.
Immediate cost: +0. No transaction.
State changes:
day → day+1: This day is done.
state stays hold: Still own the stock.
Call: max_profit(day+1, "hold")
Decision: max(sell, keep).
FROM SOLD: No choice (mandatory cooldown)
Action: Mandatory rest day after selling. No trading allowed.
Immediate cost: +0. Just waiting.
State changes:
day → day+1: This day is done.
state: sold → rest: Cooldown complete. Free to act tomorrow.
Call: max_profit(day+1, "rest")
Why is this mandatory? The problem requires waiting one day after selling before buying again. The "sold" state exists solely to enforce this one-day gap.

Step 2: States → Recursion

Each state has its own choices

def max_profit(prices, day, state, cache):
    if day == len(prices):
        return 0
    if (day, state) in cache:
        return cache[(day, state)]

    if state == "rest":
        buy = -prices[day] + max_profit(prices, day + 1, "hold", cache)
        wait = max_profit(prices, day + 1, "rest", cache)
        result = max(buy, wait)
    elif state == "hold":
        sell = prices[day] + max_profit(prices, day + 1, "sold", cache)
        keep = max_profit(prices, day + 1, "hold", cache)
        result = max(sell, keep)
    else:
        result = max_profit(prices, day + 1, "rest", cache)

    cache[(day, state)] = result
    return result

max_profit(prices, 0, "rest", {})
REST
max(buy, wait). Buy costs money now but opens future sells.
HOLD
max(sell, keep). Sell for today's price or hold for a better one.
SOLD
No choice. Must cool down. Go to REST.

The Tabulation Code

Three variables, updated each day

def max_profit(prices):
    if not prices:
        return 0

    hold = -prices[0]
    sold = 0
    rest = 0

    for day in range(1, len(prices)):
        new_hold = max(hold, rest - prices[day])
        new_sold = hold + prices[day]
        new_rest = max(rest, sold)
        hold, sold, rest = new_hold, new_sold, new_rest

    return max(sold, rest)

1 Longest Increasing Subsequence

▶
LEETCODE #300
Given an array of integers, find the length of the longest strictly increasing subsequence.
Example:
[10, 9, 2, 5, 3, 7, 101, 18]

Some increasing subsequences:
[2, 5, 7, 101] → length 4
[2, 5, 7, 18] → length 4
[2, 3, 7, 101] → length 4
[2, 5] → length 2 (valid, but not longest)

Answer: 4. No increasing subsequence of length 5 exists.
A subsequence keeps the original order but can skip elements. It doesn't have to be contiguous.
THE KEY IDEA
lis[i] = length of the longest increasing subsequence ending at index i. For each i, look at every j before it. If nums[j] < nums[i], we can extend that subsequence. Take the longest one and add 1.

Why each variable changes

State: lis_ending_at(index) = length of longest increasing subsequence ending at nums[index].

For each prev where nums[prev] < nums[index]: EXTEND
Action: Extend the subsequence ending at prev by appending nums[index].
Immediate reward: +1. Adding one more element to the subsequence.
Why can we extend? nums[prev] < nums[index], so the sequence stays strictly increasing.
State change:
index → prev: We ask "what's the best subsequence ending at prev?" to know how long the chain is before us.
Call: 1 + lis_ending_at(prev)
Why check ALL prev, not just one? Any earlier element with a smaller value could be the end of the longest chain. We don't know which prev gives the longest result until we try them all.
No valid prev exists (or standalone is best)
Action: nums[index] starts a new subsequence by itself.
Result: lis_ending_at(index) = 1. A single element is always an increasing subsequence of length 1.
Decision: best = max(1, max(1 + lis_ending_at(prev) for valid prev)). Take the longest chain we can extend, or start fresh.

Recursion

def lis_ending_at(nums, index, cache):
    if index in cache:
        return cache[index]

    best = 1
    for prev in range(index):
        if nums[prev] < nums[index]:
            best = max(best, 1 + lis_ending_at(nums, prev, cache))

    cache[index] = best
    return best

def longest_increasing(nums):
    cache = {}
    return max(lis_ending_at(nums, i, cache) for i in range(len(nums)))

Tabulation

def longest_increasing(nums):
    n = len(nums)
    lis = [1] * n

    for i in range(1, n):
        for prev in range(i):
            if nums[prev] < nums[i]:
                lis[i] = max(lis[i], lis[prev] + 1)

    return max(lis)
Not a typical state machine, but each element's "state" is the length of the best subsequence ending there. The transition: can I extend any earlier subsequence? O(n²) with DP, O(n log n) with binary search (patience sorting).

2 Burst Balloons

▶
LEETCODE #312
Given n balloons with values, burst them one at a time. When you burst balloon i, you earn nums[i-1] * nums[i] * nums[i+1] (product of it and its current neighbors). Maximize total coins. Boundaries are 1.
Example:
nums = [3, 1, 5, 8] → with boundaries: [1, 3, 1, 5, 8, 1]

One possible order:
Burst 1 (neighbors 3, 5): 3×1×5 = 15. Remaining: [3, 5, 8]
Burst 5 (neighbors 3, 8): 3×5×8 = 120. Remaining: [3, 8]
Burst 3 (neighbors 1, 8): 1×3×8 = 24. Remaining: [8]
Burst 8 (neighbors 1, 1): 1×8×1 = 8. Remaining: []

Total: 15 + 120 + 24 + 8 = 167 (this happens to be optimal).
The tricky part: when you burst a balloon, its neighbors change. Bursting [1] makes [3] and [5] become neighbors.
THE KEY IDEA
Think about which balloon to burst LAST, not first. If balloon k is the last to burst in range [left, right], the coins from k are nums[left-1] * nums[k] * nums[right+1] (the boundaries are still there because everything else in the range is already gone). This gives clean subproblems: [left, k-1] and [k+1, right].

Why each variable changes

State: max_coins(left, right) = max coins from bursting all balloons in [left, right].

For each k in [left, right]: Burst k LAST
Action: Choose balloon k to be the last one burst in the range [left, right].
Immediate reward: nums[left-1] * nums[k] * nums[right+1]. When k is the last balloon, its neighbors are the range boundaries (everything else inside is already gone).
Why LAST, not first? If we burst k first, the remaining balloons shift neighbors, making subproblems depend on each other. Bursting k last means everything else is already gone, so left-1 and right+1 are the true boundaries.
State changes:
Left subproblem: [left, k-1]. All balloons to the left of k. They are burst before k.
Right subproblem: [k+1, right]. All balloons to the right of k. Also burst before k.
Call: nums[left-1] * nums[k] * nums[right+1] + max_coins(left, k-1) + max_coins(k+1, right)
Why are subproblems independent? Since k is burst last, when we solve [left, k-1], balloon k is still there as its right boundary. When we solve [k+1, right], balloon k is still there as its left boundary. Neither subproblem affects the other's boundaries.
Base case: left > right
Action: No balloons in this range. Nothing to burst.
Result: Return 0.
Decision: best = max over all k. Try every balloon as the last one burst, keep the most profitable choice.

Recursion

def max_coins(nums, left, right, cache):
    if left > right:
        return 0
    if (left, right) in cache:
        return cache[(left, right)]

    best = 0
    for last in range(left, right + 1):
        coins = nums[left - 1] * nums[last] * nums[right + 1]
        coins += max_coins(nums, left, last - 1, cache)
        coins += max_coins(nums, last + 1, right, cache)
        best = max(best, coins)

    cache[(left, right)] = best
    return best

def burst_balloons(nums):
    nums = [1] + nums + [1]
    return max_coins(nums, 1, len(nums) - 2, {})

Tabulation

def burst_balloons(nums):
    nums = [1] + nums + [1]
    n = len(nums)
    table = [[0] * n for _ in range(n)]

    for length in range(1, n - 1):
        for left in range(1, n - length):
            right = left + length - 1
            for last in range(left, right + 1):
                coins = nums[left - 1] * nums[last] * nums[right + 1]
                coins += table[left][last - 1]
                coins += table[last + 1][right]
                table[left][right] = max(table[left][right], coins)

    return table[1][n - 2]
Interval DP: table[left][right] = max coins from bursting all balloons in [left, right]. Fill by increasing interval length (like palindrome DP). The twist: "burst last" reversal makes subproblems independent.

The State Machine Pattern

Different shapes, same idea

ProblemStatesTransitionsTable Shape
Stock + Cooldownhold, sold, rest5 arrows between states3 variables per day
LIS"best ending at i"check all j < i1D array
Burst Balloons"max coins in [l, r]"choose last to burst2D interval table
The common thread: in all three, the key insight is figuring out the RIGHT states. Stock: the constraint (cooldown) tells you the states. LIS: "ending at i" is the state. Burst Balloons: "last to burst" is the reversal that makes it work.
