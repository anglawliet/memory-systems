Two sequences, one grid. Match on the diagonal, else take the best neighbor.

The Problem

Longest Common Subsequence (LeetCode #1143)

Given two strings text1 and text2, return the length of their longest common subsequence.

text1
"abcde"
text2
"ace"
LCS = "ace", length = 3
text1 = "abc", text2 = "abc" → 3 Identical strings. Every character matches.
text1 = "abc", text2 = "def" → 0 No common characters at all.
text1 = "", text2 = "abc" → 0 Empty string. Nothing to match.
text1 = "a", text2 = "a" → 1 Single character, same in both.
text1 = "abcba", text2 = "abcbcba" → 5 text1 itself is a subsequence of text2.

1 What Is It Really Asking?

What does "subsequence" mean?

A subsequence keeps the original order but can skip characters. It does NOT need to be contiguous.

Valid subsequences of "abcde"
"ace" (skip b,d) ✓
"abcde" (skip nothing) ✓
"a" (skip b,c,d,e) ✓
"" (skip everything) ✓
NOT subsequences of "abcde"
"aec" (e comes before c in result, but after c in original) ✗
"ba" (b comes before a in result, but after a in original) ✗

What does "common" mean?

A common subsequence must be a subsequence of BOTH strings. Not just one.

Example: text1 = "abcde", text2 = "ace".
"ace" is a subsequence of text1 (skip b,d). "ace" is a subsequence of text2 (skip nothing). So "ace" is a common subsequence.
"abd" is a subsequence of text1, but NOT of text2 (text2 has no 'b' or 'd'). Not common.

What does "longest" mean?

There might be many common subsequences. We want the one with the maximum length. We return the length, not the subsequence itself.

Summary: Find the maximum number of characters I can pick from both strings such that the picked characters appear in the same order in both strings.

2 What Would I Naturally Try?

The greedy instinct

Most beginners think: "Walk through text1 left to right. For each character, grab its first available match in text2."

GREEDY ON THE EASY CASE: text1 = "abcde", text2 = "ace"
text1[0] = 'a'. Scan text2 for 'a' → found at text2[0]. Match!
text1[1] = 'b'. Scan text2 after index 0 → 'c', 'e'. No 'b'. Skip.
text1[2] = 'c'. Scan text2 after index 0 → text2[1] = 'c'. Match!
text1[3] = 'd'. Scan text2 after index 1 → 'e'. No 'd'. Skip.
text1[4] = 'e'. Scan text2 after index 1 → text2[2] = 'e'. Match!
Greedy result: "ace", length 3. Correct!

3 Where Does That Fail?

GREEDY FAILS: text1 = "cab", text2 = "abc"
text1[0] = 'c'. Scan text2 for 'c' → found at text2[2]. Match! (j moves to 3)
text1[1] = 'a'. Scan text2 after index 2 → nothing left. Skip.
text1[2] = 'b'. Scan text2 after index 2 → nothing left. Skip.
Greedy result: "c", length 1.
But the actual LCS = "ab", length 2!
text1 has 'a' at index 1, 'b' at index 2. text2 has 'a' at index 0, 'b' at index 1. In order in both strings. "ab" is a common subsequence of length 2.

What went wrong?

Greedy grabbed 'c' at position 2 in text2, consuming the entire remaining string. That was an irreversible decision. It didn't consider that skipping 'c' would leave room for the longer match "ab".

The irreversible-decision trap: Greedy picks the first match it finds and moves on. But sometimes the best move is to skip a valid match, because a different combination of matches later gives a longer result. We can't know which choices lead to the longest result without trying multiple paths.

Why brute force becomes necessary

Since we can't commit to one match greedily, we need to explore: "What if I take this match? What if I skip it?" For every matching pair, both options might lead to different outcomes. That means branching, which means recursion.

5 What Can I Do With These Two Characters?

Case 1: They match

If text1[i] == text2[j], this pair could be part of the LCS. Should I always take it?

Is there ever a reason to skip a match? No. Taking a match gives +1. Skipping it gives +0 at best. A free match is always worth taking. (This is different from Distinct Subsequences, where skipping a match can lead to more total counts. Here we're maximizing length, so a guaranteed +1 is always optimal.)

Match: Take it. Both characters consumed. +1 to the LCS. Move to lcs(i+1, j+1).

Case 2: They don't match

If text1[i] != text2[j], at least one character is useless right now. Which one should I skip? I don't know.

Two options:

Skip text1[i]: Maybe it doesn't match anything useful in text2. Move to lcs(i+1, j).
Skip text2[j]: Maybe it doesn't match anything useful in text1. Move to lcs(i, j+1).

I don't know which is better. Try both, keep the better result.

6 Why Only These Choices?

Test every idea a beginner might have

Can I skip both characters at once?
No. Skipping both throws away a character that might match something later. Maybe text1[i] matches a future text2 character, or vice versa. Skipping both is always ≤ skipping just one. It's wasteful.
Can I take a non-matching pair?
No. A common subsequence requires the same character at each position. A mismatched pair contributes nothing.
Can I jump ahead to find a match instead of skipping one at a time?
That's what the recursion does. By skipping text1[i], the next call tries text1[i+1] against text2[j]. Then text1[i+2], and so on. Each skip-one-at-a-time call explores all future matches. Jumping ahead is just multiple skips.
Can I use text1[i] to match a different character in text2 (not text2[j])?
Yes, and the recursion handles it. When I skip text2[j], the next call compares text1[i] against text2[j+1]. If that matches, great. If not, it skips again. Every possible pairing is explored.
After eliminating everything illegal:
Match? Take it. One branch. No choice needed.
No match? Skip text1[i] OR skip text2[j]. Two branches. Take the max.

10 What Does the Function Promise?

Before writing a single line, state the contract in English

lcs(i, j) returns the length of the longest common subsequence of text1[i:] and text2[j:].
What has already been decided? Everything before i in text1 and before j in text2. Those decisions are done. This function doesn't see them.
What remains available? text1[i:] and text2[j:]. All characters from i onward and from j onward.
What type of value is returned? An integer: the length (count of characters), not the subsequence itself.
The original problem: lcs(0, 0). "LCS of the full text1 and full text2."
Why does this matter? Every recursive call must preserve this promise. If I call lcs(i+1, j), it must really answer "LCS of text1[i+1:] and text2[j:]." If it doesn't, the recursion is broken.

11 When Must We Stop? (Base Cases)

If I keep making decisions, when must I eventually stop?

Don't look at the recurrence to find base cases. Ask: "What situation makes the answer trivially obvious?"

i == len(text1): text1 is exhausted
Situation: No characters left in text1.
Why stop? Can't form any common pair without characters from both strings.
Return: 0.
Why 0 and not something else? An empty string shares nothing with any string. The longest common subsequence between "" and anything is length 0.
j == len(text2): text2 is exhausted
Situation: No characters left in text2.
Why stop? Same reason. Need both strings to form a common subsequence.
Return: 0.
Symmetric: running out of either string ends the search. The answer can't grow without characters from both sides.
Why not return 1? Returning 1 would mean "I found a match," but we haven't. We're just out of characters. No match happened here.
Why not return -infinity? This isn't an "impossible" situation. It's a normal end. Running out of characters is expected.

12 What Smaller Problem Remains? (Transitions)

For each choice, what exactly changes and why?

MATCH: text1[i] == text2[j]
What did I just do? Matched one character. This character is part of the LCS.
What did I just gain? +1 to the LCS length. One character matched.
State changes:
i → i+1: text1[i] consumed. It matched. Move past it.

Why do both advance? A match consumes one character from each string. If only i advanced, text2[j] would still be available for a double-count. Both must move.
Remaining problem: 1 + lcs(i+1, j+1)
NO MATCH: text1[i] != text2[j]

Skip one character. Try both options, keep the better result.

Skip text1[i]
What did I just do? Decided text1[i] isn't useful right now. Passed over it.
What did I gain? Nothing. Skipping adds 0.

j stays: text2[j] wasn't consumed. It still needs a match from a later text1 character.
Call: lcs(i+1, j)

13 How Do We Combine the Results?

What exactly is the original question asking us to compute?

The problem says "longest." That means we want the maximum length. When I don't know which skip is better, I try both and keep whichever gives the larger result.

Match branch: adds +1 (I matched one character). Why +1? Each match contributes exactly one character to the length. Why not +2? I only matched one pair. Why not +0? I DID accomplish something: pairing two identical characters.
Skip branches: add +0 (no match, no gain). Why not +1? Skipping doesn't create a match. Nothing was paired. The skip branch adds nothing to the length.
Combining: max(skip_first, skip_second). Why max and not addition? I'm choosing ONE path, not combining two independent paths. Addition would be for counting all ways (like Distinct Subsequences). Here I want the single best path.
The pattern:
"Longest" → max().
"Count of ways" → +.
"Shortest / minimum cost" → min().
"Does any way exist?" → OR.

15 Brute-Force Code

def lcs_length(text1, text2, i, j):
    if i == len(text1) or j == len(text2):
        return 0

    if text1[i] == text2[j]:
        return 1 + lcs_length(text1, text2, i + 1, j + 1)

    skip_first = lcs_length(text1, text2, i + 1, j)
    skip_second = lcs_length(text1, text2, i, j + 1)
    return max(skip_first, skip_second)

How does a function with just (i, j) return the final answer?

Each call returns the LCS length for its remaining subproblem. lcs(2, 3) returns 0 (nothing left). lcs(1, 2) returns 1 (matched 'c'). lcs(1, 1) returns max(0, 1) = 1 (best skip).
lcs(0, 0) gets back 1 from its child, adds its own +1 for matching 'a', and returns 2. The answer builds from the bottom up through return values.

Where does repeated work appear?

Different decision paths can arrive at the same (i, j) pair. Trace the tree on "abcde" / "ace":

Different roads, same destination. Same state → same answer. Why compute it twice?

Without caching, the recursion tree has exponential branches. For strings of length m and n, it can be O(2^(m+n)) in the worst case. Each no-match call spawns TWO children, and the tree grows exponentially.

19 Memoization

Same state (i, j) always produces the same answer. Cache it.

Cache key: (i, j). The state. The minimum unique identifier.
Cache value: The LCS length for that state. An integer.
Total entries: At most m × n, where m = len(text1), n = len(text2).
def lcs_length(text1, text2, i, j, cache):
    if i == len(text1) or j == len(text2):
        return 0
    if (i, j) in cache:
        return cache[(i, j)]

    if text1[i] == text2[j]:
        result = 1 + lcs_length(text1, text2, i + 1, j + 1, cache)
    else:
        skip_first = lcs_length(text1, text2, i + 1, j, cache)
        skip_second = lcs_length(text1, text2, i, j + 1, cache)
        result = max(skip_first, skip_second)

    cache[(i, j)] = result
    return result
Teal: Cache lookup
Before computing, check if (i, j) was already solved. If yes, return immediately. This is what eliminates repeated work.
Teal: Cache store
After computing, save the result before returning. Future calls with the same (i, j) will hit the lookup.
What changed? Three lines added (lookup, store, pass cache). The recurrence is unchanged. The answer is unchanged. Only the runtime changed: from exponential to O(m × n).

20 Tabulation

Why the table dimensions come from the state

State = (i, j). Two state variables → two table dimensions. i ranges from 0 to len(text1). j ranges from 0 to len(text2). So the table is (len(text1)+1) × (len(text2)+1).

What does table[i][j] mean? The LCS length for text1[:i] and text2[:j]. (Note: tabulation uses prefix convention, not suffix. table[0][anything] = 0, because an empty prefix of text1 has no characters to match.)

Base cases become initialized cells

First row (i=0): empty text1 prefix. LCS = 0 for any text2 prefix.
First column (j=0): empty text2 prefix. LCS = 0 for any text1 prefix.
Both are already 0 from initialization.

Which cells does each transition depend on?

table[i-1][j-1] (diagonal, for match)
table[i-1][j] (up, for skip text1[i])
table[i][j-1] (left, for skip text2[j])

All three are above or to the left. So filling row by row, left to right guarantees every dependency has already been computed.

The code

def lcs_length(text1, text2):
    rows = len(text1)
    cols = len(text2)
    table = [[0] * (cols + 1) for _ in range(rows + 1)]

    for i in range(1, rows + 1):
        for j in range(1, cols + 1):
            if text1[i - 1] == text2[j - 1]:
                table[i][j] = table[i - 1][j - 1] + 1
            else:
                table[i][j] = max(table[i - 1][j], table[i][j - 1])

    return table[rows][cols]

All zeros. First row and column = base cases (empty prefix has LCS = 0). No separate initialization loop needed.
Brown: Iteration order
Row by row, left to right. Dependencies (up, left, diagonal) are always filled before the current cell.
Orange: Match → diagonal + 1
Same as recursion: match consumes both characters. In the table, "both consumed" means look diagonally (one row up, one column left).
Red: No match → max(up, left)

Purple: Return the answer

21 Space Optimization

Which previous states are actually needed?

Each cell uses three neighbors: table[i-1][j-1], table[i-1][j], table[i][j-1]. All from the current row or the row directly above. No cell ever looks at two rows back.

Keep only two rows: the previous row and the current row. After filling the current row, the previous row becomes the new "previous" and the old one is discarded. Space drops from O(m × n) to O(min(m, n)).
Does update direction matter? We fill left to right. curr_row[j-1] is already filled (left). prev_row[j] and prev_row[j-1] are from the previous row (already complete). No conflict. 
def lcs_length(text1, text2):
    if len(text2) > len(text1):
        text1, text2 = text2, text1
    cols = len(text2)
    prev_row = [0] * (cols + 1)
    curr_row = [0] * (cols + 1)

    for i in range(1, len(text1) + 1):
        for j in range(1, cols + 1):
            if text1[i - 1] == text2[j - 1]:
                curr_row[j] = prev_row[j - 1] + 1
            else:
                curr_row[j] = max(prev_row[j], curr_row[j - 1])
        prev_row, curr_row = curr_row, [0] * (cols + 1)

    return prev_row[cols]
What clarity is lost? We can no longer trace back through the full table to reconstruct the actual LCS string. Only the length is recoverable. If you need the subsequence itself, keep the full table.

22 Common Mistakes

Adding +1 on the skip branch
return 1 + lcs(i+1, j) ← WRONG
Skipping doesn't match anything. No character was paired. +0, not +1.
Detection: lcs("a", "b") returns 1 instead of 0.
Using addition instead of max on no-match
return lcs(i+1, j) + lcs(i, j+1) ← WRONG
Addition counts all paths. That's for "number of ways" problems (like Distinct Subsequences). Here we want the single longest, so max().
Detection: lcs("ab", "cd") returns a number greater than the shorter string's length.
Only advancing one pointer on match
return 1 + lcs(i+1, j) or return 1 + lcs(i, j+1) ← WRONG
A match consumes one from EACH string. If only i advances, text2[j] remains available and the same character gets matched again later. Double-counting.
Detection: lcs("a", "a") returns more than 1.
Returning 1 for the base case instead of 0
if i == len(text1): return 1 ← WRONG
Running out of characters isn't a success. It's the end. No match happened here. Return 0.
Detection: lcs("a", "b") returns 1 instead of 0.
Wrong table iteration order
Filling bottom-to-top or right-to-left with the standard recurrence. Each cell needs up, left, and diagonal. If the row above isn't filled yet, the values are wrong.
Detection: The table produces different results than the recursive solution on the same input.

text1[i] == text2[j] in the tabulation loop ← WRONG

1 What Is It Really Asking?

What counts as a "unique path"?

A path is a specific sequence of moves, each one either down or right, starting at (row 0, col 0) and ending at (row rows-1, col cols-1). Two paths are different if the sequence of moves differs anywhere, even if they visit the same number of cells.

Legal moves
Down: move from (row, col) to (row+1, col).
Right: move from (row, col) to (row, col+1).
Illegal moves
Up, left, diagonal, staying in place, leaving the grid boundary. None of these are allowed.
Why does move order matter?

On a 2x2 grid, both paths use one down and one right move, but "right then down" and "down then right" pass through different intermediate cells. They are counted as two separate paths, not one.

Summary: Count every distinct sequence of down/right moves that starts at the top-left cell and ends at the bottom-right cell without ever leaving the grid.

2 What Would I Naturally Try?

There's no greedy temptation here, unlike LCS. Every path reaches the same destination no matter which moves get picked, so there's no "wrong" choice to fall for. The natural first attempt is simpler and blunter: "I'll just draw every path and count them."

3 Where Does That Fail?

MANUAL COUNTING COLLAPSES: rows = 10, cols = 10
Every path needs exactly 9 down moves and 9 right moves, in some order. The number of distinct orderings is 18 choose 9 = 48,620. Drawing 48,620 paths by hand isn't just tedious, it's impossible in any reasonable time.
What went wrong?

Manual counting doesn't fail because of a wrong idea, it fails because of scale. The number of paths grows combinatorially with grid size. Listing every path is fine for a 2x3 grid and impossible for a 10x10 grid, even though the rule ("down or right") never changed.

The scale trap: I don't need to enumerate every path to count them. I need a way to count paths without listing them. That means breaking the problem into smaller versions of itself: "how many paths from here?" instead of "what does every path look like?"
Why recursion becomes necessary

If I stand at any cell, the number of paths to the destination from that cell doesn't depend on how I got there. It only depends on where I am now. That's a strong hint: define a function of "where I am" and let it call itself on smaller grids.

6 Why Only These Choices?

Can the robot move up or left?
No. The problem statement only allows down and right. Moving up or left would revisit territory and could loop forever, and it isn't a legal action for this robot.
Can the robot move diagonally?
No. Diagonal isn't down or right. It would also skip over cells, changing what "unique path" means. Not a legal move.
Can the robot stay in place?
No. Staying doesn't make progress toward the destination, and "unique path" implies a finite sequence of moves that ends. Staying forever isn't a path.
Can the robot teleport several cells at once?
No. Each move advances exactly one cell, down or right. Multi-cell jumps aren't legal moves, and they'd change which paths get counted.
What if down or right leaves the grid?
Then that move isn't available. This isn't a third choice, it's a boundary condition. It shows up as the out-of-bounds base case (Step 12), not as a new kind of move.
After eliminating everything illegal:
Exactly two moves remain from any cell: down, right. No conditions decide between them, both are always tried (when in bounds).

10 What Does the Function Promise?

Before writing a single line, state the contract in English
count_paths(row, col) returns the number of unique paths from (row, col) to the destination (rows-1, cols-1).
What has already been decided? Everything before (row, col): how the robot got there. This function doesn't see it and doesn't need to.
What remains available? The sub-grid from (row, col) down to (rows-1, cols-1).
What type of value is returned? An integer count of paths, not a list of the paths themselves.

11 When Must We Stop? (Base Cases)

If the robot keeps moving, when must it eventually stop?

Don't look at the recurrence to find base cases. Ask: "What situation makes the answer trivially obvious?"

row == rows-1 and col == cols-1: reached the destination
Situation: The robot is standing exactly on the bottom-right cell.
Why stop? It's already there. No more moves needed. This is one complete, valid path.
Return: 1.
Why 1 and not 0? Reaching the destination IS a success, it's one way of arriving. Returning 0 would say "no path exists here," which is false, the robot is standing on a valid endpoint.
row ≥ rows or col ≥ cols: out of bounds
Situation: The robot tried to step off the edge of the grid.
Why stop? This cell doesn't exist. No further moves are possible from here.
Return: 0.
Why 0 and not 1? An illegal position contributes nothing. It represents a move that shouldn't have been taken, so it adds no paths to the total.
Why not swap them? Destination = 1 because it's a real, countable path. Out of bounds = 0 because it's not a real position at all. Mixing these up (returning 0 at the destination, or 1 out of bounds) breaks the count immediately, see Step 23.

13 How Do We Combine Futures?

What exactly is the original question asking us to compute?

The problem says "count the number of unique paths." Both the down-branch and the right-branch lead to a destination, and every path through the down-branch is different from every path through the right-branch (they diverge at this very cell). To count everything, I need both sets of paths, not just the bigger one.

Down branch: count_paths(row+1, col) paths. Every single one is a distinct, complete path through this cell.
Right branch: count_paths(row, col+1) paths. Also each distinct and complete.
Combining: down + right. Why addition and not max? I'm not choosing the single best path here, I'm counting ALL of them. Every path counted by the down branch is a valid, separate path. Every path counted by the right branch is also valid and separate. None overlap (a path either goes down first or right first from this cell, never both). Add them.
The pattern:
"Longest / shortest / best" → max() or min(). Choosing one path.
"Count of ways" → +. Every branch is a separate valid outcome, none excludes another.
"Does any way exist?" → OR.
This is the key difference from LCS: there, "longest" forced a choice (max) between two exclusive options. Here, "count" forces us to keep both (add), because down-first and right-first are two genuinely different, non-overlapping sets of paths.

How does a function with just (row, col) return the final answer?
Each call returns the path count for its own remaining subproblem. count_paths(1,2) returns 1 (it's the destination). count_paths(1,1) returns 0+1=1 (its two branches summed).

18 Why Is It Slow?

Where does repeated work appear?

The trace above already showed it: count_paths(1, 1) got computed twice, once from count_paths(1, 0)'s right-branch, and once from count_paths(0, 1)'s down-branch. count_paths(1, 2) got computed twice as well.

(1, 1) is reachable from (0, 0) two different ways: down-then-right, or right-then-down
Different move sequences, same destination cell. Same state → same answer. Why compute it twice?

In general, cell (row, col) is reachable from the start by any interleaving of row down-moves and col right-moves. All of those different histories collapse into the same recursive call. Without caching, this is exactly the combinatorial explosion from Step 4, showing up again inside the recursion tree, with branching that can reach O(2^(rows+cols)) calls in the worst case.

19 Memoization

Same state (row, col) always produces the same answer. Cache it.

Cache key: (row, col). The state. The minimum unique identifier.
Cache value: The number of paths from that cell. An integer.
Total entries: At most rows × cols.
def count_paths(rows, cols, row, col, cache):
    if row == rows - 1 and col == cols - 1:
        return 1
    if row >= rows or col >= cols:
        return 0
    if (row, col) in cache:
        return cache[(row, col)]

    move_down = count_paths(rows, cols, row + 1, col, cache)
    move_right = count_paths(rows, cols, row, col + 1, cache)

    cache[(row, col)] = move_down + move_right
    return cache[(row, col)]
Teal: Cache lookup
Before computing, check if (row, col) was already solved. If yes, return immediately. This is what eliminates the duplicate work seen in Step 18.
Teal: Cache store
After computing, save the result before returning. Future calls with the same (row, col) will hit the lookup instead of recomputing.
What changed? Three lines added (lookup, store, pass cache). The recurrence is unchanged. The answer is unchanged. Only the runtime changed: from exponential to O(rows × cols).

20 Tabulation

Why the table dimensions come from the state

State = (row, col). Two state variables → two table dimensions. The table is rows × cols, exactly the grid itself.

What does table[row][col] mean? The number of paths from the start (0,0) TO (row, col). Note the flip: the recursion counted paths from (row,col) to the destination (a suffix view). The table instead counts paths from the start to (row,col) (a prefix view). Both are valid ways to fill the same grid, table[row][col] here means "ways to arrive," not "ways to finish."
Base cases become initialized cells

First row (row=0): the robot can only have arrived by moving right the whole way. Exactly 1 way.
First column (col=0): the robot can only have arrived by moving down the whole way. Exactly 1 way.
Both get initialized to 1, not computed from a formula.

Which cells does each transition depend on?
table[row-1][col] (up, arriving by a final down move)
table[row][col-1] (left, arriving by a final right move)

Both are above or to the left. So filling row by row, left to right guarantees every dependency has already been computed.

def count_paths(rows, cols):
    table = [[1] * cols for _ in range(rows)]

    for row in range(1, rows):
        for col in range(1, cols):
            table[row][col] = table[row - 1][col] + table[row][col - 1]

    return table[rows - 1][cols - 1]
Pink: Table initialization
Every cell starts at 1, not 0. This looks unusual, but it's a shortcut: the first row and first column need to be 1 (Step 20's base cases), and initializing everything to 1 handles those automatically. The loop below then overwrites every cell that isn't in the first row or column.
Brown: Iteration order
Row by row, left to right, starting from row 1 and col 1 (skipping the pre-filled base row/column). Dependencies (up, left) are always filled before the current cell.
Orange: The single rule
Every interior cell is up + left. No conditions. This mirrors the recursion's move_down + move_right, just viewed from the opposite direction (arriving instead of leaving).
Purple: Return the answer
Bottom-right corner: the destination. The answer to the original problem.

21 Space Optimization

Which previous states are actually needed?

Each cell uses two neighbors: table[row-1][col] and table[row][col-1]. Both come from the current row or the row directly above. No cell ever looks two rows back.

Keep only one row: a single 1D array can do the whole job. table[row][col-1] is just "the value I already wrote earlier in this same pass" (still in the array, to the left). table[row-1][col] is "the value from the previous row" (still sitting at that index, not yet overwritten). Space drops from O(rows × cols) to O(cols). 
def count_paths(rows, cols):
    row_values = [1] * cols

    for row in range(1, rows):
        for col in range(1, cols):
            row_values[col] = row_values[col] + row_values[col - 1]

    return row_values[cols - 1]
Why does updating in place still work? Before the assignment, row_values[col] holds last row's value (up). row_values[col-1] already got overwritten earlier in this same inner loop pass, so it holds this row's value (left). Both pieces needed are exactly where the algorithm expects them, no extra array required.

22 Common Mistakes

Returning 0 at the destination instead of 1
if row == rows-1 and col == cols-1: return 0 ← WRONG
Reaching the destination is a successful path, not a dead end. It must contribute 1 to the total, not 0.
Detection: count_paths on a 1x1 grid returns 0 instead of 1.
Using max instead of add
return max(move_down, move_right) ← WRONG
max() picks the single best path, which is what "longest" problems like LCS need. This problem says "count," meaning every path matters, not just the biggest branch. Use addition.

Wrong base case for out-of-bounds
if row >= rows or col >= cols: return 1 ← WRONG
An out-of-bounds cell isn't a valid position, let alone a valid path. It must contribute 0, not 1. Returning 1 here silently inflates the count for every path that goes off the edge.

Off-by-one in grid dimensions
if row == rows and col == cols: return 1 ← WRONG
The destination is (rows-1, cols-1), the last valid index, not (rows, cols), which is already out of bounds. This condition would never trigger, since the out-of-bounds check fires first.

Wrong table iteration order

This is the simplest member of the 2D table family: no match/no-match split, no min/max decision, just addition of neighbors. It's also the combinatorics connection: the first row and column of 1s, with each interior cell as the sum of its neighbors, is exactly Pascal's triangle rotated 45 degrees. Obstacle-grid variants (LeetCode #63) just add a third condition: if the cell is blocked, force it to 0 regardless of its neighbors.

2 Edit Distance

▶

The Problem

Edit Distance (LeetCode #72)

Given two strings word1 and word2, return the minimum number of operations required to convert word1 into word2. You may insert a character, delete a character, or replace a character. Each operation costs 1.

word1
"horse"
word2
"ros"
Minimum operations = 3
replace 'h'→'r', delete 'r', delete 'e': "horse" → "rorse" → "rorse" (drop r) → "rose" → "ros"
word1 = "horse", word2 = "ros" → 3 One replace, two deletes.
word1 = "intention", word2 = "execution" → 5 Three replaces, one delete, one insert.
word1 = "abc", word2 = "abc" → 0 Identical strings. Nothing to change.
word1 = "", word2 = "abc" → 3 Empty string. Every character of word2 must be inserted.
word1 = "a", word2 = "b" → 1 Single character, different. One replace.

1 What Is It Really Asking?

What do the three operations actually do?
Insert: add one new character anywhere into word1. Word1 grows by one.
Delete: remove one character from word1. Word1 shrinks by one.
Replace: swap one character in word1 for a different character. Word1's length is unchanged.

Every operation, no matter which one, costs exactly 1. A word with five wrong characters isn't automatically five operations. The question is: what is the fewest operations that turn word1 into word2, using any mix of these three moves in any order?

Summary: Find the minimum total count of single-character edits (insert, delete, or replace) needed to transform word1 into word2, exactly.

2 What Would I Naturally Try?

The greedy instinct

Most beginners think: "Walk through both strings left to right at the same time. Where the characters already match, do nothing. Where they don't, replace the word1 character to fix it."

GREEDY ON AN EASY CASE: word1 = "abc", word2 = "abd"
Position 0: 'a' vs 'a'. Match, do nothing.
Position 1: 'b' vs 'b'. Match, do nothing.
Position 2: 'c' vs 'd'. Mismatch, replace.
Greedy result: 1 operation. Correct!

Same length, same positions lining up, one mismatch fixed with one replace. It feels like the whole problem. But now try two strings of different lengths.

3 Where Does That Fail?

GREEDY FAILS: word1 = "abc", word2 = "abdc"
Position 0: 'a' vs 'a'. Match.
Position 1: 'b' vs 'b'. Match.
Position 2: word1 has 'c', word2 has 'd'. Mismatch, replace 'c' with 'd'. word1 is now "abd".
Position 3: word1 is out of characters, word2 still has 'c' left. Insert 'c'.
Greedy result: 2 operations (1 replace + 1 insert).
But the actual minimum is 1 operation!
Just insert 'd' between 'b' and 'c': "abc" → "abdc" = "abdc". Done. One insert, not a replace-then-insert combo.
What went wrong?

Greedy assumed word1 and word2 stay aligned position-by-position: word1[i] always compared against word2[i]. But once word1 and word2 have different lengths, that alignment breaks. Replacing 'c' with 'd' locked in a rigid one-to-one pairing that wasn't the cheapest way to line the strings up. Skipping ahead in word2 (inserting) would have realigned things for free.

The rigid-alignment trap: Greedy always compares position i in word1 to position i in word2, then fixes mismatches with replace. But sometimes the cheaper move is to shift the alignment itself, by inserting or deleting, not just editing in place. We can't know which operation realigns the strings best without trying all three at every mismatch.
Why brute force becomes necessary

Since I can't commit to "always replace" on a mismatch, I need to explore: "What if I replace here? What if I delete? What if I insert?" Each choice changes the alignment differently. That means branching, which means recursion.

4 What Decision Am I Stuck On?

Freeze inside one recursive call

Imagine I'm at position i in word1 and position j in word2. I see two characters: word1[i] and word2[j].

What is preventing me from finishing?

I need to decide: what do I do about word1[i] and word2[j]? The answer depends on whether they're already the same character. If they match, is there ever a reason to spend an operation here? If they don't match, which operation fixes it cheapest? That's the natural first check: do these two characters already agree?

5 What Can I Do With These Two Characters?

Case 1: They match

If word1[i] == word2[j], word1 already has the right character sitting at position i. Is there ever a reason to spend an operation here anyway? No. Replacing a correct character with itself is a wasted operation. Inserting or deleting around a correct character just to redo it later never helps. A free match is always worth taking for free.

Match: Do nothing. No operation. +0 cost. Both characters handled. Move to min_edits(i+1, j+1).
Case 2: They don't match

If word1[i] != word2[j], something has to be spent here. But which operation? I don't know yet, so consider all three.

Three options, each costing 1:

Replace word1[i] with word2[j]. Move to min_edits(i+1, j+1).
Delete word1[i] entirely. Move to min_edits(i+1, j).
Insert word2[j] into word1. Move to min_edits(i, j+1).

I don't know which is cheapest overall. Try all three, keep the smallest result.

6 Why Only These Choices?

Test every idea a beginner might have
Can I spend zero operations on a mismatch?
No. The problem defines exactly three legal moves. Leaving a mismatch unresolved means word1 never becomes word2. Something must change.
Can I do two operations at once, like replace-and-insert, for a single unit of cost?
No. Every operation, by definition, costs exactly 1 and touches one character. Combining moves is just two operations charged twice, which the recursion already explores by chaining calls (a delete followed by an insert, for instance).
Can I reorder characters instead of inserting/deleting/replacing?
No. Reordering isn't one of the allowed operations. The only way to change position is to delete from one place and insert somewhere else, which the recursion already models as two separate unit-cost moves.
Could there be a fourth useful operation, like "swap two adjacent characters"?
Not for this problem. LeetCode #72 defines exactly insert, delete, replace. Some variants of edit distance add a swap operation, but that changes the recurrence; we only have these three here.
After eliminating everything illegal:
Match? Do nothing. One branch. No choice needed.
No match? Replace, delete, or insert. Three branches. Take the minimum.

10 What Does the Function Promise?

Before writing a single line, state the contract in English
min_edits(i, j) returns the minimum number of operations to convert word1[i:] into word2[j:].
What has already been decided? Everything before i in word1 and before j in word2. Those edits are done. This function doesn't see them.
What remains available? word1[i:] and word2[j:]. Everything from i onward and from j onward.
What type of value is returned? An integer: a count of operations, not the edited string itself.
The original problem: min_edits(0, 0). "Minimum operations to turn the full word1 into the full word2."
Why does this matter? Every recursive call must preserve this promise. If I call min_edits(i+1, j), it must really answer "minimum ops to turn word1[i+1:] into word2[j:]." If it doesn't, the recursion is broken.

11 When Must We Stop? (Base Cases)

If I keep making decisions, when must I eventually stop?

Don't look at the recurrence to find base cases. Ask: "What situation makes the answer trivially obvious?"

i == len(word1): word1 is exhausted
Situation: No characters left in word1, but word2[j:] might still have characters.
Why stop? There's nothing left to match, delete, or replace. The only remaining move is to insert whatever's left of word2.
Return: len(word2) - j.
Why that number and not 0? Unlike LCS, running out of one string doesn't end the work. Every leftover character in word2 still needs a dedicated insert.
j == len(word2): word2 is exhausted
Situation: word2 is fully produced, but word1[i:] might still have leftover characters.
Why stop? There's nothing left to produce. Any remaining word1 characters are just extra baggage that must be removed.
Return: len(word1) - i.
Every leftover character in word1 needs a dedicated delete.
Why not return 0 like LCS does? LCS just needs to stop counting matches, so 0 is correct. Edit Distance still owes work: leftover characters on either side must be individually inserted or deleted. Ignoring them would undercount the cost.
What if both i and len(word1) and j and len(word2) hit at once? Then len(word2) - j = 0 or len(word1) - i = 0. Either base case correctly returns 0, since there's nothing left on both sides.

13 How Do We Combine the Results?

What exactly is the original question asking us to compute?

The problem says "minimum number of operations." That means the smallest total cost. When I don't know which of the three moves is cheapest, I try all of them and keep whichever gives the smaller result.

Match branch: adds +0 (nothing to fix). Why not +1? No operation happened. Charging a cost for doing nothing would overcount.
Replace / delete / insert branches: each adds +1 (one operation spent). Why exactly 1, never more, never less? The problem defines every operation as unit cost, regardless of which one.
Combining: min(replace, delete, insert). Why min and not max, and not addition? I'm choosing ONE sequence of edits, not summing three separate attempts, and I want the cheapest one, not the most expensive. "Minimum operations" is a direct instruction to minimize.
The pattern:
"Longest / most" → max().
"Count of ways" → +.
"Shortest / minimum cost / fewest operations" → min().
"Does any way exist?" → OR.

Where does repeated work appear?

19 Memoization

Same state (i, j) always produces the same answer. Cache it.

Cache key: (i, j). The state. The minimum unique identifier.
Cache value: The minimum edit cost for that state. An integer.
Total entries: At most (m+1) × (n+1), where m = len(word1), n = len(word2).
def min_edits(word1, word2, i, j, cache):
    if i == len(word1):
        return len(word2) - j
    if j == len(word2):
        return len(word1) - i
    if (i, j) in cache:
        return cache[(i, j)]

    if word1[i] == word2[j]:
        result = min_edits(word1, word2, i + 1, j + 1, cache)
    else:
        replace = min_edits(word1, word2, i + 1, j + 1, cache)
        delete = min_edits(word1, word2, i + 1, j, cache)
        insert = min_edits(word1, word2, i, j + 1, cache)
        result = 1 + min(replace, delete, insert)

    cache[(i, j)] = result
    return result
Teal: Cache lookup
Before computing, check if (i, j) was already solved. If yes, return immediately. This is what eliminates repeated work, and there's more of it to eliminate here than in LCS, since each mismatch fans out into three children instead of two.
Teal: Cache store
After computing, save the result before returning. Future calls with the same (i, j) will hit the lookup.
What changed? Three lines added (lookup, store, pass cache). The recurrence is unchanged. The answer is unchanged. Only the runtime changed: from exponential to O(m × n).

20 Tabulation

Why the table dimensions come from the state

State = (i, j). Two state variables → two table dimensions. i ranges from 0 to len(word1). j ranges from 0 to len(word2). So the table is (len(word1)+1) × (len(word2)+1).

What does table[i][j] mean? The minimum edits to turn word1[:i] into word2[:j]. (Note: tabulation uses prefix convention, not suffix. This flips the direction of the base cases.)
Base cases become initialized edges, not zeros

First row (i=0): empty word1 prefix. Turning "" into word2[:j] takes exactly j inserts. So table[0][j] = j.
First column (j=0): empty word2 prefix. Turning word1[:i] into "" takes exactly i deletes. So table[i][0] = i.
Unlike LCS, these edges are NOT all zero. They count straight up from 0 to the row or column index.

table[i-1][j-1] (diagonal, for match or replace)
table[i-1][j] (up, for delete)
table[i][j-1] (left, for insert)

All three are above or to the left. So filling row by row, left to right guarantees every dependency has already been computed.

j=5 (word2[4]='e'): 'o' != 'e'. 1 + min(table[1][4], table[1][5], table[2][4]) = 1 + min(3, 4, 3) = 4.

def min_edits(word1, word2):
    rows = len(word1)
    cols = len(word2)
    table = [[0] * (cols + 1) for _ in range(rows + 1)]

    for i in range(rows + 1):
        table[i][0] = i
    for j in range(cols + 1):
        table[0][j] = j

    for i in range(1, rows + 1):
        for j in range(1, cols + 1):
            if word1[i - 1] == word2[j - 1]:
                table[i][j] = table[i - 1][j - 1]
            else:
                table[i][j] = 1 + min(
                    table[i - 1][j - 1],
                    table[i - 1][j],
                    table[i][j - 1]
                )

    return table[rows][cols]

Not all zeros this time. All zeros first, then the edges are overwritten with the base cases.
Brown: Edges and iteration order
table[i][0] = i and table[0][j] = j are the base cases written directly into the table, not initialized to 0 like LCS. Then row by row, left to right, so dependencies (up, left, diagonal) are always filled before the current cell.
Green: Match → diagonal, no +1
Same as recursion: a match is free. In the table, "free and both consumed" means copy the diagonal value exactly, no addition.
Red: No match → 1 + min(diag, up, left)

Purple: Return the answer

21 Space Optimization

Which previous states are actually needed?

Each cell uses three neighbors: table[i-1][j-1], table[i-1][j], table[i][j-1]. All from the current row or the row directly above. No cell ever looks at two rows back.

Keep only two rows: the previous row and the current row. After filling the current row, the previous row becomes the new "previous" and the old one is discarded. Space drops from O(m × n) to O(min(m, n)).
Does the row's own starting value need special handling? Yes. curr_row[0] must be set to i at the start of every row, since that's the base case for an empty word2 prefix at this word1 length. It's not carried over from prev_row.

22 Common Mistakes

Forgetting +1 on the operation branches
replace = min_edits(i+1, j+1) used directly as the final answer, without adding 1 ← WRONG
Every operation costs 1. Forgetting to add it means the function counts matches but not edits.
Detection: min_edits("a", "b") returns 0 instead of 1.
Using max instead of min
return 1 + max(replace, delete, insert) ← WRONG
The problem asks for the minimum number of operations, the cheapest path. Max would find the most expensive way to do it, backwards.
Detection: min_edits("horse", "ros") returns something far larger than 3, often close to the combined string length.
Copying LCS's base case of 0
if i == len(word1): return 0 ← WRONG
Unlike LCS, running out of word1 doesn't mean "nothing more to do." If word2 still has characters left, each one needs a dedicated insert. The correct base case is len(word2) - j, not 0.
Detection: min_edits("", "abc") returns 0 instead of 3.
Mixing up which pointer moves for insert vs delete
insert = min_edits(i+1, j) or delete = min_edits(i, j+1) ← WRONG (swapped)
Delete removes a word1 character, so i advances (min_edits(i+1, j)). Insert adds a word2 character into word1, so j advances (min_edits(i, j+1)). Swapping them makes the recursion track the wrong string's progress.
Detection: min_edits("abc", "abdc") stops returning 1 and starts returning something inconsistent across similar insert-only cases.
Adding +1 on a match
return 1 + min_edits(i+1, j+1) when word1[i] == word2[j] ← WRONG
A match needs no operation. Charging for it inflates the answer even on identical strings.
Detection: min_edits("abc", "abc") returns 3 instead of 0.
Wrong tabulation edge initialization
Leaving table[i][0] and table[0][j] at 0 (LCS-style) instead of setting them to i and j.
Detection: The tabulated answer is consistently lower than the recursive answer on the same input, especially when the strings differ in length.

23 Pattern Recognition

What clues suggested DP?
"Minimum number of operations" = optimization. Two strings = two dimensions. Greedy fails because a fix at one position changes what's optimal at the next. Different decision paths converge on the same state.
What uncertainty forced branching?
On a mismatch, I don't know whether replace, delete, or insert is cheapest overall. That uncertainty creates three branches instead of LCS's two.
What caused overlapping subproblems?
Deleting then matching and inserting-then-matching can both land on the same (i, j) as a direct replace. Different edit sequences, same remaining subproblem.
Which operator follows from the question wording?
"Minimum" → min(). "Longest" would mean max(). "Count of ways" would mean addition.
When I see _______, I should consider _______:
When I see "two strings" + "transform one into the other" + "minimum operations", I should consider two-pointer DP with a free match and a min() over several unit-cost edits on mismatch.
What generalizes?
Edit Distance is the same grid as LCS, with three differences: match is free instead of +1, the combining operator is min instead of max, and mismatch spawns three choices instead of two because there are three operations instead of two skips. The base cases flip too: running out of a string here still costs work (insert or delete the rest), where in LCS it costs nothing.

24 Rediscover It Six Months Later

How would I reinvent this from scratch?
1 "Two strings, three allowed edits, minimum total. Let me try greedy: walk both strings together, replace on any mismatch."
2 "Greedy fails once the strings have different lengths, because always-replace assumes rigid position-by-position alignment. Sometimes inserting or deleting realigns things cheaper."
3 "So I'm stuck: at each pair of characters, do they already match? If yes, do nothing, it's free. If no, which operation fixes it cheapest? I don't know, so try replace, delete, and insert, all three."
4 "My state is just (i, j), two pointers. My function promises 'minimum ops to turn word1[i:] into word2[j:].' Base case: word1 runs out, insert the rest of word2; word2 runs out, delete the rest of word1."

The reasoning process, not the code. Even if the recurrence is completely forgotten, walking through these six steps will reconstruct it, and the LCS comparison (free match becomes +0, max becomes min, two skips become three operations) rebuilds the rest.

3 Interleaving String

▶

The Problem

Interleaving String (LeetCode #97)

Given strings s1, s2, and s3, determine if s3 can be formed by interleaving s1 and s2. Interleaving means: take characters from s1 and s2, keeping the relative order within each string, so that they combine into s3.

s1
"aab"
s2
"axy"
s3 = "aaxaby" → True
aaxaby (s1 chars in order, s2 chars in order)
s1 = "aab", s2 = "axy", s3 = "abxy" → False Even though every letter of s3 appears somewhere in s1 or s2, there is no way to interleave them in order and land on exactly "abxy".
s1 = "", s2 = "abc", s3 = "abc" → True An empty s1 contributes nothing. s3 must equal s2 exactly.
s1 = "", s2 = "", s3 = "" → True Nothing to interleave, nothing to form. Trivially true.
s1 = "ab", s2 = "c", s3 = "abcd" → False len(s1) + len(s2) = 3, but len(s3) = 4. The lengths don't even add up, so no interleaving can possibly work.

1 What Is It Really Asking?

What does "interleaving" actually require?

Strip away the vocabulary. The real question is: can I pick characters from s1 and s2, one at a time, and lay them down in some order, such that the result is exactly s3?

Allowed
Reordering WHEN you draw from s1 versus s2. s1 = "ab", s2 = "cd" can form "acbd", "abcd", "cabd", "cdab", and more.
NOT allowed
Reordering characters WITHIN s1 or WITHIN s2. s1 = "ab" can never contribute a "b" before an "a". That internal order is locked.

Every character of s3 needs a source

s3 is built one character at a time. Every single character in s3 must be explained: did it come from the next unused character of s1, or the next unused character of s2? There's no third option, and no character can be skipped or invented.

Summary: Consume s1 and s2 from left to right (never out of order), interleaving them any way I like, and check whether the result matches s3 exactly, character for character.

2 What Would I Naturally Try?

The greedy instinct

Most beginners think: "Walk through s3 left to right. For each position, whichever string's next character matches, take it from there."

GREEDY ON THE EASY CASE: s1 = "ab", s2 = "cd", s3 = "acbd"
s3[0] = 'a'. s1[0] = 'a' matches. s2[0] = 'c' doesn't. Take from s1. (i=1)
s3[1] = 'c'. s1[1] = 'b' doesn't match. s2[0] = 'c' matches. Take from s2. (j=1)
s3[2] = 'b'. s1[1] = 'b' matches. s2[1] = 'd' doesn't. Take from s1. (i=2)
s3[3] = 'd'. s1 exhausted. s2[1] = 'd' matches. Take from s2. (j=2)
Greedy result: True. Correct! At every step, only ONE string ever matched, so there was never a real decision to make.

Greedy works here because it was never actually tested. Now try an input where both strings match the same character at the same time.

3 Where Does That Fail?

GREEDY FAILS: s1 = "aax", s2 = "aay", s3 = "aayaax"
s3[0] = 'a'. s1[0] = 'a' matches. s2[0] = 'a' also matches. Greedy needs a tie-break, say "prefer s1." Take from s1. (i=1)
s3[1] = 'a'. s1[1] = 'a' matches. s2[0] = 'a' also matches. Same tie-break. Take from s1. (i=2)
s3[2] = 'y'. s1[2] = 'x' doesn't match. s2[0] = 'a' doesn't match either. Dead end. No source for 'y'.
Greedy result: False.
But the actual answer is True!
Take all of s2 first, then all of s1: aayaax = "aayaax" = s3. A valid interleaving exists. Greedy's tie-break just picked the wrong one.

What went wrong?

At s3[0] and s3[1], BOTH s1 and s2 offered a matching 'a'. Greedy committed to s1 both times, an irreversible decision. By the time it reached s3[2] = 'y', it had already used up s1's "aa" and had no way back to try s2 first.

The irreversible-decision trap: when the next character of s3 matches BOTH s1[i] and s2[j], greedy has to guess which one to consume. Guess wrong, and later characters have no source left. We can't know which guess is safe without trying both.

Why brute force becomes necessary

Since a single guess can silently doom the rest of the string, we need to explore: "What if this character came from s1? What if it came from s2?" Whenever both are possible, both paths must be tried. That means branching, which means recursion.

4 What Decision Am I Stuck On?

Freeze inside one recursive call

Imagine I've already consumed i characters from s1 and j characters from s2. That means s3 must have absorbed exactly i + j characters so far. Call that position k = i + j.

s1
a a x
i is here. Everything before is consumed.
s2
a a y
j is here. Everything before is consumed.
What is preventing me from finishing?

s3[k] is the next character I must produce, and I know exactly what it is. But I have TWO candidate sources sitting right in front of me: s1[i] and s2[j]. If both happen to equal s3[k], which one actually supplied it? I can't tell from the character alone.

5 What Can I Do?

Check each candidate source, one at a time

There is no matching-pair concept here like in LCS. There's just one target character, s3[i+j], and up to two places it could have come from.

If s1[i] == s3[i+j]: s1 could have supplied this character. Try taking from s1. Move to can_interleave(i+1, j).
If s2[j] == s3[i+j]: s2 could have supplied this character. Try taking from s2. Move to can_interleave(i, j+1).
If neither matches: nobody can supply s3[i+j]. This path is dead. Return False immediately, don't keep exploring it.

Notice this is not "skip a character" the way LCS skips a mismatch. There is no skipping. Every character of s3 must be accounted for by exactly one source, right now, at this position.

6 Why Only These Choices?

Test every idea a beginner might have

Can I leave s3[i+j] unexplained and come back to it?
No. s3 is being built left to right, one character per step. Position i+j must be resolved before position i+j+1 can even be discussed. Skipping is not an option here, unlike LCS.
Can s3[i+j] come from a character deeper in s1 or s2, not s1[i] or s2[j]?
No. s1 and s2 must be consumed strictly in order. s1[i] is the very next unused character of s1. Nothing before it is available (already used), and nothing after it can jump the queue.
Can I take from BOTH s1 and s2 at once for this one character?
No. Each position in s3 is exactly one character, and it needs exactly one source. Taking from both would mean producing two characters for one slot.
What if neither s1[i] nor s2[j] matches?
Then this branch is impossible. There's no third source to fall back on. Return False, don't invent a way forward.
After eliminating everything illegal:
s1[i] matches? Try it. s2[j] matches? Try it. Neither matches? Dead end, False. At most two branches, sometimes zero, never more than two.

10 What Does the Function Promise?

Before writing a single line, state the contract in English

can_interleave(i, j) returns True if s1[i:] and s2[j:] can be interleaved to form s3[i+j:].
What has already been decided? Everything before i in s1, before j in s2, and before i+j in s3. Those characters are locked in.
What remains available? s1[i:], s2[j:], and the target s3[i+j:].
What type of value is returned? A boolean. True or False, not a count or a length.
The original problem: can_interleave(0, 0). "Can the full s1 and full s2 interleave to form the full s3?"
Why does this matter? Every recursive call must preserve this promise. If I call can_interleave(i+1, j), it must really answer "can s1[i+1:] and s2[j:] form s3[i+j+1:]?" That only works because k = i+j updates automatically to i+1+j.

11 When Must We Stop? (Base Cases)

If I keep making decisions, when must I eventually stop?

Don't look at the recurrence to find base cases. Ask: "What situation makes the answer trivially obvious?"

i + j == len(s3): every position in s3 has been explained
Situation: Nothing left in s3 to account for.
Why stop? The job was to explain every character of s3. If we're out of characters, we're done.
Return: i == len(s1) and j == len(s2).
Why check i and j too? Because the upfront length check guarantees len(s1)+len(s2) == len(s3). If i+j == len(s3), then (len(s1)-i) + (len(s2)-j) must equal 0, which forces i == len(s1) and j == len(s2). This condition is really just a safety statement of "both strings are also fully consumed," which is always true here, but it's the honest way to phrase what "done" means.
Neither s1[i] nor s2[j] matches s3[i+j]
Situation: The next character of s3 has no possible source.
Why stop? There's nothing left to try from this state. Continuing would mean inventing a character out of nowhere.
Return: False.
This isn't really a separate "base case" line in code, it falls out naturally: if neither guarded if-branch fires, result simply stays False.
A third check, done once before recursion even starts: if len(s1) + len(s2) != len(s3), return False immediately. No interleaving can ever produce a string of the wrong length, so don't waste a single recursive call finding that out the slow way.

13 How Do We Combine Futures?

What exactly is the original question asking us to compute?

The problem asks "can s3 be formed," not "how many ways" or "what's the best way." That's an existence question. If EITHER the take-from-s1 path or the take-from-s2 path leads to success, the whole thing succeeds.

Take from s1 branch: only attempted if s1[i] == s3[i+j]. If s1 doesn't match, this branch isn't even tried; it isn't "False," it's simply absent.
Take from s2 branch: only attempted if s2[j] == s3[i+j]. Same reasoning.
Combining: result_from_s1 OR result_from_s2. Why OR and not AND? We only need ONE valid interleaving to exist, not both branches to work. Why not max/min? There's no quantity to compare, only a yes/no per path.
The pattern:
"Longest / shortest" → max() / min().
"Count of ways" → +.
"Does any way exist?" → OR. That's exactly this problem.

    try s2: can_interleave(1, 1)

    can_interleave(1, 1)  k=2, s3[2]='b'. s1[1]='b' matches. s2[1]='d' no match.
      try s1: can_interleave(2, 1)

      can_interleave(2, 1)  k=3, s3[3]='d'. s1 exhausted (i=2). s2[1]='d' matches.
        try s2: can_interleave(2, 2)

        can_interleave(2, 2)  i+j=4=len(s3). i==len(s1) and j==len(s2). Return True.
      Return True.
    Return True.
  Return True.
Return True.

How does a boolean function without a running total return the final answer?

Each call answers True/False for exactly its own remaining subproblem. can_interleave(2,2) answers True because there's nothing left to explain. That True flows straight back up: no accumulation, no arithmetic, just propagation.
At every level, if the chosen source's recursive call returned True, this level also returns True immediately. There's never a need to check the OTHER source once one path succeeds.

18 Why Is It Slow?

Where does repeated work appear?

Whenever s3[i+j] matches BOTH s1[i] and s2[j], the call branches in two directions. Different sequences of branch choices can land on the exact same (i, j) pair.

can_interleave("aax", "aay", "aayaax", 0, 0)
  both match 'a': try (1,0) AND try (0,1)
    (1,0): both match 'a' again: try (2,0) AND try (1,1)
    (0,1): both match 'a' again: try (1,1) AND try (0,2)
                                        +
                              (1,1) reached from BOTH paths!
can_interleave(1, 1) computed from two different branch paths
Different roads, same destination. Same state → same answer. Why compute it twice?

Without caching, every tie between s1[i] and s2[j] doubles the number of calls. For strings of length m and n, the worst case is O(2^(m+n)), exponential.

19 Memoization

Same state (i, j) always produces the same boolean. Cache it.

Cache key: (i, j). The state. k is never part of the key, it's implied.
Cache value: True or False for that state.
Total entries: At most (len(s1)+1) × (len(s2)+1).
def can_interleave(s1, s2, s3, i, j, cache):
    if i + j == len(s3):
        return i == len(s1) and j == len(s2)
    if (i, j) in cache:
        return cache[(i, j)]

    result = False
    if i < len(s1) and s1[i] == s3[i + j]:
        result = can_interleave(s1, s2, s3, i + 1, j, cache)
    if not result and j < len(s2) and s2[j] == s3[i + j]:
        result = can_interleave(s1, s2, s3, i, j + 1, cache)

    cache[(i, j)] = result
    return result
Teal: Cache lookup
Before computing, check if (i, j) was already solved. If yes, return immediately.
Teal: Cache store
After computing, save the result before returning. Future calls with the same (i, j) hit the lookup instead of re-exploring both branches.
What changed? The recurrence is unchanged, the answer is unchanged. Only the runtime changed: from exponential to O(len(s1) × len(s2)).

20 Tabulation

Why the table dimensions come from the state

State = (i, j). Two state variables → two table dimensions. i ranges from 0 to len(s1). j ranges from 0 to len(s2). So the table is (len(s1)+1) × (len(s2)+1), exactly like LCS's table, even though this problem returns booleans, not counts.

What does table[i][j] mean? True if s1[:i] and s2[:j] can interleave to form s3[:i+j]. (Prefix convention, same as LCS: table[0][0] = True, empty + empty = empty.)

Base cases become initialized cells

First row (i=0): only s2 supplies characters. table[0][j] = True only if table[0][j-1] is True AND s2[j-1] matches s3[j-1].
First column (j=0): only s1 supplies characters. table[i][0] = True only if table[i-1][0] is True AND s1[i-1] matches s3[i-1].
table[0][0] = True: nothing to interleave, nothing to form.

Which cells does each transition depend on?

table[i-1][j] (up, for "take from s1")
table[i][j-1] (left, for "take from s2")

No diagonal dependency this time (that's the LCS-specific move for a simultaneous match). Both dependencies are above or to the left. So filling row by row, left to right guarantees every dependency is already computed.

The code

def can_interleave(s1, s2, s3):
    if len(s1) + len(s2) != len(s3):
        return False
    rows = len(s1)
    cols = len(s2)
    table = [[False] * (cols + 1) for _ in range(rows + 1)]
    table[0][0] = True

    for j in range(1, cols + 1):
        table[0][j] = table[0][j - 1] and s2[j - 1] == s3[j - 1]
    for i in range(1, rows + 1):
        table[i][0] = table[i - 1][0] and s1[i - 1] == s3[i - 1]

    for i in range(1, rows + 1):
        for j in range(1, cols + 1):
            from_s1 = table[i - 1][j] and s1[i - 1] == s3[i + j - 1]
            from_s2 = table[i][j - 1] and s2[j - 1] == s3[i + j - 1]
            table[i][j] = from_s1 or from_s2

    return table[rows][cols]
Pink: Setup and length guard
The length check from Step 11, now run once at the top instead of implicitly inside every call. table[0][0] = True is the only cell that starts True; everything else starts False.
Brown: First row and first column
These are the base cases where one string is completely unused. Each cell can only be True if the previous cell in the same row/column was True AND the next character matches. One mismatch anywhere breaks the whole row or column, since only one source is available.
Green: Take from s1
Look up. Was (i-1, j) reachable, and does s1[i-1] supply the needed character?
Blue: Take from s2
Look left. Was (i, j-1) reachable, and does s2[j-1] supply the needed character?
Purple: Combine and return

21 Space Optimization

Which previous states are actually needed?

Each cell uses exactly two neighbors: table[i-1][j] (the row above) and table[i][j-1] (the current row, one column back). No diagonal, no two-rows-back. Just like LCS but with one fewer dependency.

Keep only one row: since the current cell only reads the cell directly above it (previous row) and the cell directly to its left (same row, already updated), a single 1D array can serve as both, exactly the way the LCS space optimization uses one row. Space drops from O(len(s1) × len(s2)) to O(min(len(s1), len(s2))).
Does update direction matter? We fill left to right. row[j-1] is already the NEW value from this same row (take from s2). row[j], before we overwrite it, is still the OLD value from the row above (take from s1). We must read row[j] before writing it. 
def can_interleave(s1, s2, s3):

22 Common Mistakes

Forgetting the length pre-check
Without if len(s1) + len(s2) != len(s3): return False, the recursion or tabulation may run against a target that can never be reached, wasting time or even reading past the end of s3.
Detection: s1 = "a", s2 = "b", s3 = "ab" then s3 = "abc" crashes or loops instead of returning False cleanly.
Introducing k as a separate parameter or loop variable
def can_interleave(s1, s2, s3, i, j, k): ← WRONG (redundant)
k is not new information. It's always i + j. Carrying it separately invites bugs where i, j, and k drift out of sync after an update to only one of them.
Detection: after incrementing i but forgetting to increment k, s3 lookups silently point at the wrong character.
Off-by-one between i+j (0-indexed) and the tabulation table (1-indexed)
s3[i + j] inside the tabulation loop ← WRONG
In tabulation, table[i][j] represents i and j characters already consumed, so the NEXT character to check is s3[i + j - 1], not s3[i + j]. The recursive version uses 0-indexed i, j directly; tabulation shifts by one.
Detection: IndexError, or the table quietly checks the wrong character and produces a False where True is correct.
Treating a no-match as "skip" instead of "return False"
if s1[i] != s3[i+j] and s2[j] != s3[i+j]: return can_interleave(i+1, j) ← WRONG
This problem has no skip move, unlike LCS. If neither source can supply the required character, that path is truly dead, not "try again later." Silently advancing i anyway fabricates a character that was never verified against s3.
Detection: the function returns True for interleavings that don't actually reconstruct s3 when you print the characters used.
Using AND instead of OR to combine the two branches
return branch_s1 and branch_s2 ← WRONG
We need only ONE valid interleaving, not both branches to independently succeed (they can't both succeed simultaneously anyway, since taking from s1 and taking from s2 are alternatives for the SAME character, not two separate requirements).
Detection: valid interleavings that only work through one specific branch get rejected.

23 Pattern Recognition

What clues suggested DP?
"Can it be formed" = boolean existence question. Two source strings merging into one target = two dimensions. Greedy fails whenever both sources offer the same next character.
What uncertainty forced branching?
When s1[i] and s2[j] BOTH equal s3[i+j], I don't know which one actually supplied it. That uncertainty creates two branches.
What caused overlapping subproblems?
Different tie-break sequences can land on the same (i, j) after consuming the same total number of characters from each string, even though they got there in a different order.
Which operator follows from the question wording?
"Can it be formed" → OR(). "Count the ways" would mean addition. "Longest / shortest" would mean max/min.
The k = i + j insight, generalized
Whenever a target sequence is built by merging two source sequences in order, the position in the target is always the SUM of how far you've progressed in each source. That's one fewer state dimension than you'd expect: 2D, not 3D.
When I see _______, I should consider _______:
When I see "two sources merge into one target, in order" + "does a valid arrangement exist", I should consider 2D boolean DP where the target index is derived, not stored, and branches are OR'd together.
What generalizes?
Compare to LCS: both use a 2D grid over two input strings. But LCS's third string is the ANSWER (the subsequence itself, implicit in the count), while here the third string is a GIVEN constraint that must be matched exactly. That's why LCS can skip mismatches (nothing forces every character to be used) while Interleaving String cannot (every character of s3 must be explained by something).

24 Rediscover It Six Months Later

How would I reinvent this from scratch?

1 "Three strings, but only s1 and s2 are real inputs. s3 is the target. Let me try greedy: always take from whichever string matches next."
2 "Greedy fails whenever BOTH s1 and s2 match the same next character, because committing to the wrong one can strand me later with no source for what comes next."
3 "So at each point, check: does s1[i] match s3's next character? Does s2[j]? If neither, dead end, False. If either (or both), try that path and recurse."
4 "My state is just (i, j). I don't need a third variable for position in s3, because i + j always tells me that. My function promises 'can the remaining suffixes of s1 and s2 form the remaining suffix of s3?' Base case: i+j == len(s3), succeed only if i == len(s1) and j == len(s2)."
5 "Take from s1 moves i. Take from s2 moves j. Never both, never neither. Combine with OR, because I just need ANY valid interleaving to exist, not to count or optimize."
6 "Different branch orders reach the same (i, j). Overlapping subproblems. Cache it, or build a 2D boolean table filled row by row: table[i][j] = (came from s1's row above) OR (came from s2's column to the left). One row of space suffices since I only ever look up or left."
The reasoning process, not the code. Even if the recurrence is completely forgotten, walking through these six steps, especially remembering that k = i + j needs no storage, will reconstruct it.

4 Distinct Subsequences

▶

1 The Problem

LEETCODE #115
Given two strings source and target, return the number of distinct subsequences of source that equal target.
source = "rabbbit", target = "rabbit" → 3 source has three b's. target needs two. Three different pairs of b's can be chosen.
source = "babgbag", target = "bag" → 5 three b's, two a's, two g's in source. Five distinct index-combinations spell "bag".
source = "aaa", target = "a" → 3 pick the first 'a', or the second, or the third. Three separate ways.
source = "xyz", target = "abc" → 0 not a single character of target appears in source. No way to spell it.
source = "abc", target = "abc" → 1 only one way: use every character of source, in order.

2 What Is It Really Asking?

Strip away the word "subsequence" for a moment. What am I actually being asked to count?

Reframed: "In how many different ways can I walk through source left to right, marking some characters as used and the rest as skipped, such that the used characters, read in order, spell exactly target?"

Two ways are "different" if they use a different set of positions in source, even if the characters look identical. In source = "aaa", target = "a", using index 0 and using index 1 are different ways, even though both produce the letter "a".

source plays a flexible role
It's the pool of characters I'm choosing from. I can use or skip each character of source.
target plays a fixed role
It's the template I must spell out exactly, in order, with no gaps and no omissions.

Keep that asymmetry in mind. It shapes almost every decision in this problem.

3 What Would I Naturally Try?

The natural first instinct: scan source left to right. Keep a pointer into target. Whenever the current source character equals the next unmatched target character, grab it immediately and advance both pointers. When the target pointer reaches the end, I've found a subsequence.

GREEDY ON AN EASY CASE: source = "rabbit", target = "rabbit"
source[0]='r' matches target[0]='r'. Use it.
source[1]='a' matches target[1]='a'. Use it.
... continue matching every character in lockstep.
target fully matched. Greedy reports: found 1 way.

That looks right, so it's tempting to generalize: "always grab a match the moment I see one." Seems reasonable, seems fast. Let's test it somewhere less trivial.

4 Where Does That Fail?

GREEDY FAILS: source = "aab", target = "ab"
source[0]='a' matches target[0]='a'. Grab it immediately. Target pointer moves to 'b'.
source[1]='a' does not match target[1]='b'. Skip it.
source[2]='b' matches target[1]='b'. Grab it. target fully matched.
Greedy result: 1 way (used index 0 and index 2).
But the actual answer is 2!
There's a second, equally valid way: skip index 0's 'a', use index 1's 'a' instead, then use index 2's 'b'. That also spells "ab", using a different set of positions. Greedy never considered it, because it committed to the first 'a' the instant it saw one.

What went wrong?

Greedy treated "use the first match" as free, since using a match costs nothing and only helps. But that reasoning only holds if I'm trying to find one way. Here I need to count every way. Committing to one specific source index for target[0] silently throws away every other way that could have used a different index for target[0].

The irreversible-decision trap: greedy locks in "use this exact character" the moment it finds a match, and never revisits that choice. But skipping a match and using a later duplicate is often just as valid, and leads to a genuinely different subsequence. Since I need the total count of all valid subsequences, I can't commit early. I need to explore both "use it" and "skip it" at every match, and count what each path finds.

5 What Decision Am I Stuck On?

Freeze inside one recursive call

Imagine I'm standing at position i in source and position j in target. Everything before i has already been decided (used or skipped). Everything before j has already been matched. I look at source[i] and target[j], and they happen to be the same character.

source
a a b b i t
i is here. Everything before is decided.
target
a b
j is here. Everything before is matched.
What is preventing me from finishing?

source[i] equals target[j]. It's a valid, legal match right now. But should I use it to satisfy target[j], or skip it and hope a later occurrence of this same character also matches target[j]? Both are legal moves at this exact instant. I don't know which one (or both) contributes to the final count.

6 What Can I Do?

Case 1: source[i] matches target[j]

Two genuinely different, both-legal moves.

Use it: source[i] satisfies target[j]. Both consumed. Move to count_ways(i+1, j+1).
Skip it: save source[i] and hope a later character also matches target[j]. Only source advances. Move to count_ways(i+1, j).

Case 2: source[i] does not match target[j]

source[i] cannot possibly stand in for target[j]. There's no decision to make. Only one legal move.

Only option: skip source[i]. Move to count_ways(i+1, j).

7 Why Only These Choices?

Test every idea a beginner might have

Can I skip a character of target?
No. target is the fixed spelling I'm required to produce, character for character. Skipping one would mean I'm no longer forming target at all, but something shorter.
Can I reorder characters, or use a source character out of position?
No. A subsequence must preserve the relative order of source. Once I move past source[i], it's gone. I can never come back for it.
Can I reuse the same source character for two positions of target?
No. Each index in source can be used at most once. That's exactly why the pointer i only ever moves forward, one step at a time.
Can I use source[i] when it doesn't match target[j]?
No. That would spell the wrong character into target. Illegal by definition.
After eliminating everything illegal:
Match? Use it OR skip it. Two branches. Count both.
No match? Skip it. One branch. No decision left.

Notice: j only ever advances when a character is actually used. i advances on every branch, since every step examines one more source character and decides its fate.

11 What Does the Function Promise?

Before writing a single line, state the contract in English

count_ways(i, j) returns the number of distinct subsequences of source[i:] that equal target[j:].
What has already been decided? Everything before i in source and every character of target before j. Those decisions are locked in and off-screen from this call.
What remains available? source[i:] to pick from, target[j:] to spell.
What type of value is returned? An integer count of distinct ways, never the subsequences themselves.
The original problem: count_ways(0, 0). "Number of ways to spell all of target using all of source."

12 When Must We Stop?

Before thinking about choices, ask: "When is the answer obvious without any recursion?"

j == len(target): all of target is matched
Situation: Nothing left in target to spell.
Why stop? The job is already done, regardless of what's left in source.
Return: 1. This IS one complete, valid way.
NOT 0. Reaching the end of target is success, so it counts as one way, even if source[i:] is empty too.
i == len(source): ran out of source characters
Situation: source is exhausted, but target[j:] still has unmatched characters.
Why stop? There's nothing left to pick from. Impossible to finish spelling target.
Return: 0. No way to complete the match.
Check j == len(target) FIRST. If both are exhausted at once, the correct answer is 1 (success), not 0.

13 What Smaller Problem Remains?

CASE: source[i] == target[j] (Match)

Two legal options. Count both paths.

Option 1: USE source[i] to satisfy target[j]
State changes:
i → i+1: source[i] consumed, used for the match.
j → j+1: target[j] matched. Move to the next target character.
Call: count_ways(i+1, j+1)
Why both advance? Using source[i] to satisfy target[j] resolves one character from each string in a single move.
Option 2: SKIP source[i] (even though it matches)
State changes:
i → i+1: source[i] discarded, not used.
j stays the same: target[j] is still unmatched, waiting for a later source character.
Call: count_ways(i+1, j)
Why doesn't j change? I chose not to spend this character on target[j]. It still needs to be matched by something later in source.
Combine: result = use + skip. Both are genuinely distinct sets of used positions, so both get counted.
CASE: source[i] != target[j] (No Match)
Only legal move: skip source[i]. It cannot stand in for target[j].
State changes:
i → i+1: source[i] discarded, useless for the current target character.
j stays the same: target[j] still waiting to be matched.
Call: count_ways(i+1, j)

14 How Do We Combine Futures?

What exactly is the original question asking us to compute?

The problem says "the number of distinct subsequences." That's a count, not a best-of. Every legal branch produces a different, valid set of used positions in source. None of them is "better" than another. I'm not choosing the winner. I'm counting all the winners.

Match branch: use contributes count_ways(i+1, j+1) ways, skip contributes count_ways(i+1, j) ways. Every way counted by "use" is different from every way counted by "skip", because they disagree on whether source[i] is part of the subsequence.
Combining: use + skip. Why add and not max? Because I need the total count of every valid way, not the single best one. Max would throw away all but one path, undercounting exactly like greedy did in Step 4.
The pattern:
"Longest / shortest" (LCS, Edit Distance) → max() / min(). Choosing one best path.
"Number of distinct ways" (this problem) → +. Counting every valid path.
"Does any way exist?" → OR.

15 The Recurrence

Now it writes itself

Every branch has already been justified. The recurrence is just a compact summary:

                ┌ 1                                             if j == len(target)
count_ways(i,j)=│ 0                                             if i == len(source)

Line 3: Match. Use it AND skip it. Add both counts (Steps 13, 14).
Line 4: No match. Only skip is legal (Steps 13, 14).

19 Why Is It Slow?

Where does repeated work appear?

The trace above already caught it: count_ways(2, 1) was computed twice, once from count_ways(1, 0)'s match branch, once from count_ways(1, 1)'s skip branch. Different sequences of decisions, same (i, j) landing spot.

Every match creates two branches. With k matching characters along the way, the call tree can branch up to 2^k times, and many of those branches collide on the same (i, j) pair, especially when source has repeated characters (like "aaa" or "bbb"), which is exactly the case this problem is built around.

Same signal as every DP problem: the state is only (i, j), just two numbers, but the number of distinct call paths that reach a given (i, j) grows exponentially. Whenever a small, fixed-size state gets revisited by exponentially many paths, that's overlapping subproblems, and it's the cue to cache.

20 Memoization

def count_ways(source, target, i, j, cache):
    if j == len(target):
        return 1
    if i == len(source):
        return 0
    if (i, j) in cache:
        return cache[(i, j)]

    ways = count_ways(source, target, i + 1, j, cache)
    if source[i] == target[j]:
        ways += count_ways(source, target, i + 1, j + 1, cache)

    cache[(i, j)] = ways
    return ways
One line added, one line changed. Check the cache right after the base cases, before doing any recursive work. Store the result right before returning. Every (i, j) pair now gets computed exactly once, dropping the runtime from exponential to O(len(source) × len(target)).

21 Tabulation

TABLE MAPPING
table[i][j] = count_ways(i, j) = number of ways to spell target[j:] using source[i:].
Row i ranges 0 to len(source). Col j ranges 0 to len(target).

Base cases in the table:
table[i][len(target)] = 1 for every i: an empty remaining target is always already spelled.
table[len(source)][j] = 0 for j < len(target): an empty remaining source can never finish a non-empty target.

Because count_ways(i, j) is defined on suffixes (source[i:], target[j:]), table[i][j] depends on row i+1, the row for one more character consumed. So rows must be filled from the bottom up: start at i = len(source) and work back to i = 0. This is the mirror image of LCS's forward fill, and it falls straight out of the same forward-indexing recursion, no re-deriving needed.

def count_ways(source, target):
    source_length = len(source)
    target_length = len(target)
    table = [[0] * (target_length + 1) for _ in range(source_length + 1)]

    for i in range(source_length + 1):
        table[i][target_length] = 1

    for i in range(source_length - 1, -1, -1):
        for j in range(target_length - 1, -1, -1):
            table[i][j] = table[i + 1][j]
            if source[i] == target[j]:
                table[i][j] += table[i + 1][j + 1]

    return table[0][0]

Line by line, this is the recurrence with count_ways(i+1, j) renamed to table[i+1][j], and count_ways(i+1, j+1) renamed to table[i+1][j+1]. Nothing new was invented, only the recursive calls became array lookups.

22 Space Optimization

Every cell table[i][j] only reads from row i+1. Row i never reads from itself. That means one row can be reused for every value of i, as long as it's updated in the right direction.

The subtle part: within a row, table[i][j] depends on row[j] and row[j+1], both still holding old (row i+1) values. If j is updated in increasing order (0, 1, 2, ...), then when row[j] is written, row[j+1] hasn't been touched yet this round, so it's still the old value. Updating j in decreasing order would corrupt row[j+1] before it's read. This is the opposite direction from problems where matches read from j-1. 
def count_ways(source, target):
    source_length = len(source)
    target_length = len(target)
    row = [0] * (target_length + 1)
    row[target_length] = 1

    for i in range(source_length - 1, -1, -1):
        for j in range(target_length):
            if source[i] == target[j]:
                row[j] += row[j + 1]

    return row[0]

Trace it on source="aab", target="ab": start row = [0, 0, 1]. i=2 ('b'): j=1 matches, row becomes [0, 1, 1]. i=1 ('a'): j=0 matches, row becomes [1, 1, 1]. i=0 ('a'): j=0 matches, row becomes [2, 1, 1]. Return row[0] = 2. Same answer, O(len(target)) space instead of O(len(source) × len(target)).

23 Common Mistakes

Using max instead of +
return max(use, skip) ← WRONG
That's the LCS habit. This problem counts ways, it doesn't choose a best one. Every legal branch is a distinct, valid answer that must be added, not compared.
Detection: count_ways("aaa", "a") returns 1 instead of 3.
Advancing target on a mismatch
if source[i] != target[j]: return count_ways(i+1, j+1) ← WRONG
target[j] can only be considered matched when a source character was actually used for it. A mismatch means nothing happened to target; only source moves.
Detection: answers become smaller than they should be, or even negative-feeling nonsense on strings with no common characters.
Swapping the two base case values
if j == len(target): return 0 and if i == len(source): return 1 ← WRONG
Backwards. Finishing target is success (1). Running out of source first is failure (0).
Detection: count_ways("abc", "abc") returns 0 instead of 1.
Forgetting the skip branch on a match
if source[i] == target[j]: return count_ways(i+1, j+1) ← WRONG (missing the skip term)
This is the exact greedy failure from Step 4. It finds at most one way per state instead of adding in every duplicate-character alternative.
Detection: count_ways("aab", "ab") returns 1 instead of 2.
Iterating j in the wrong direction during space optimization
In the 1D version, updating j from high to low overwrites row[j+1] with a new (row i) value before it's read for row[j], silently corrupting the count.
Detection: the 1D version disagrees with the 2D tabulation on the same input, usually undercounting.

24 Pattern Recognition

What clues suggested DP?
"Number of distinct ways" = counting. Two strings = two dimensions. Greedy fails because an early commitment to one match blocks other valid completions.
What uncertainty forced branching?
At a match, I don't know whether using this exact index or saving it for a later duplicate leads to more total completions. That uncertainty is exactly why both get explored and added.
What caused overlapping subproblems?
"Use then skip" and "skip then use" can land on the exact same (i, j). Same remaining suffixes, different history.
Which operator follows from the question wording?
"Number of ways" → +. "Longest" would mean max(). "Fewest operations" would mean min().
What made this asymmetric, unlike LCS?
source and target don't play the same role. source is negotiable, characters can be used or skipped. target is fixed, every character must be matched, none can be skipped. That one-sided skipping is what separates this problem's shape from LCS's two-sided skipping.
When I see _______, I should consider _______:
When I see "count the number of distinct ways" + "subsequence" + one string that must be fully matched against another that can be partially used, I should consider one-sided-skip counting DP with addition.

25 Rediscover It Six Months Later

How would I reinvent this from scratch?

1 "Two strings, count the ways to spell one from the other. Let me try scanning and grabbing every match greedily."
2 "Greedy fails on repeated characters, like 'aab'/'ab'. Grabbing the first match blocks a different, equally valid match through a later duplicate."
3 "So at each pair: does source[i] match target[j]? If yes, I have two legal moves, use it or skip it, and both matter, so I add them. If no, skip is the only move."
4 "My state is (i, j). My function promises 'ways to spell target[j:] from source[i:].' Base cases: target used up means 1 (success), source used up first means 0 (failure), and check target first."
5 "Match: use + skip, both advance i, only use advances j. No match: skip only. 'Number of ways' means addition, not max."
6 "Different decision paths reach the same (i, j). Overlapping subproblems, cache it. Two positions, two strings, one grid, but only source can be skipped, so the table fills from the bottom row up."
The reasoning process, not the code. Even if the recurrence is completely forgotten, walking through these six steps will reconstruct it: greedy fails on duplicates, a match creates a real use-or-skip choice, target is fixed while source is negotiable, and "count of ways" always means addition.
