Two sequences, one grid. Match on the diagonal, else take the best neighbor.

The Problem

Longest Common Subsequence (LeetCode #1143)

Given two strings text1 and text2, return the length of their longest common subsequence.

text1
"abcde"
text2
"ace"
LCS = "ace", length = 3
text1 = "abc", text2 = "abc" → 3 Identical strings. Every character matches.
text1 = "abc", text2 = "def" → 0 No common characters at all.
text1 = "", text2 = "abc" → 0 Empty string. Nothing to match.
text1 = "a", text2 = "a" → 1 Single character, same in both.
text1 = "abcba", text2 = "abcbcba" → 5 text1 itself is a subsequence of text2.

1 What Is It Really Asking?

What does "subsequence" mean?

A subsequence keeps the original order but can skip characters. It does NOT need to be contiguous.

Valid subsequences of "abcde"
"ace" (skip b,d) ✓
"abcde" (skip nothing) ✓
"a" (skip b,c,d,e) ✓
"" (skip everything) ✓
NOT subsequences of "abcde"
"aec" (e comes before c in result, but after c in original) ✗
"ba" (b comes before a in result, but after a in original) ✗

What does "common" mean?

A common subsequence must be a subsequence of BOTH strings. Not just one.

Example: text1 = "abcde", text2 = "ace".
"ace" is a subsequence of text1 (skip b,d). "ace" is a subsequence of text2 (skip nothing). So "ace" is a common subsequence.
"abd" is a subsequence of text1, but NOT of text2 (text2 has no 'b' or 'd'). Not common.

What does "longest" mean?

There might be many common subsequences. We want the one with the maximum length. We return the length, not the subsequence itself.

Summary: Find the maximum number of characters I can pick from both strings such that the picked characters appear in the same order in both strings.

2 What Would I Naturally Try?

The greedy instinct

Most beginners think: "Walk through text1 left to right. For each character, grab its first available match in text2."

GREEDY ON THE EASY CASE: text1 = "abcde", text2 = "ace"
text1[0] = 'a'. Scan text2 for 'a' → found at text2[0]. Match!
text1[1] = 'b'. Scan text2 after index 0 → 'c', 'e'. No 'b'. Skip.
text1[2] = 'c'. Scan text2 after index 0 → text2[1] = 'c'. Match!
text1[3] = 'd'. Scan text2 after index 1 → 'e'. No 'd'. Skip.
text1[4] = 'e'. Scan text2 after index 1 → text2[2] = 'e'. Match!
Greedy result: "ace", length 3. Correct!

3 Where Does That Fail?

GREEDY FAILS: text1 = "cab", text2 = "abc"
text1[0] = 'c'. Scan text2 for 'c' → found at text2[2]. Match! (j moves to 3)
text1[1] = 'a'. Scan text2 after index 2 → nothing left. Skip.
text1[2] = 'b'. Scan text2 after index 2 → nothing left. Skip.
Greedy result: "c", length 1.
But the actual LCS = "ab", length 2!
text1 has 'a' at index 1, 'b' at index 2. text2 has 'a' at index 0, 'b' at index 1. In order in both strings. "ab" is a common subsequence of length 2.

What went wrong?

Greedy grabbed 'c' at position 2 in text2, consuming the entire remaining string. That was an irreversible decision. It didn't consider that skipping 'c' would leave room for the longer match "ab".

The irreversible-decision trap: Greedy picks the first match it finds and moves on. But sometimes the best move is to skip a valid match, because a different combination of matches later gives a longer result. We can't know which choices lead to the longest result without trying multiple paths.

Why brute force becomes necessary

Since we can't commit to one match greedily, we need to explore: "What if I take this match? What if I skip it?" For every matching pair, both options might lead to different outcomes. That means branching, which means recursion.

5 What Can I Do With These Two Characters?

Case 1: They match

If text1[i] == text2[j], this pair could be part of the LCS. Should I always take it?

Is there ever a reason to skip a match? No. Taking a match gives +1. Skipping it gives +0 at best. A free match is always worth taking. (This is different from Distinct Subsequences, where skipping a match can lead to more total counts. Here we're maximizing length, so a guaranteed +1 is always optimal.)

Match: Take it. Both characters consumed. +1 to the LCS. Move to lcs(i+1, j+1).

Case 2: They don't match

If text1[i] != text2[j], at least one character is useless right now. Which one should I skip? I don't know.

Two options:

Skip text1[i]: Maybe it doesn't match anything useful in text2. Move to lcs(i+1, j).
Skip text2[j]: Maybe it doesn't match anything useful in text1. Move to lcs(i, j+1).

I don't know which is better. Try both, keep the better result.

6 Why Only These Choices?

Test every idea a beginner might have

Can I skip both characters at once?
No. Skipping both throws away a character that might match something later. Maybe text1[i] matches a future text2 character, or vice versa. Skipping both is always ≤ skipping just one. It's wasteful.
Can I take a non-matching pair?
No. A common subsequence requires the same character at each position. A mismatched pair contributes nothing.
Can I jump ahead to find a match instead of skipping one at a time?
That's what the recursion does. By skipping text1[i], the next call tries text1[i+1] against text2[j]. Then text1[i+2], and so on. Each skip-one-at-a-time call explores all future matches. Jumping ahead is just multiple skips.
Can I use text1[i] to match a different character in text2 (not text2[j])?
Yes, and the recursion handles it. When I skip text2[j], the next call compares text1[i] against text2[j+1]. If that matches, great. If not, it skips again. Every possible pairing is explored.
After eliminating everything illegal:
Match? Take it. One branch. No choice needed.
No match? Skip text1[i] OR skip text2[j]. Two branches. Take the max.

10 What Does the Function Promise?

Before writing a single line, state the contract in English

lcs(i, j) returns the length of the longest common subsequence of text1[i:] and text2[j:].
What has already been decided? Everything before i in text1 and before j in text2. Those decisions are done. This function doesn't see them.
What remains available? text1[i:] and text2[j:]. All characters from i onward and from j onward.
What type of value is returned? An integer: the length (count of characters), not the subsequence itself.
The original problem: lcs(0, 0). "LCS of the full text1 and full text2."
Why does this matter? Every recursive call must preserve this promise. If I call lcs(i+1, j), it must really answer "LCS of text1[i+1:] and text2[j:]." If it doesn't, the recursion is broken.

11 When Must We Stop? (Base Cases)

If I keep making decisions, when must I eventually stop?

Don't look at the recurrence to find base cases. Ask: "What situation makes the answer trivially obvious?"

i == len(text1): text1 is exhausted
Situation: No characters left in text1.
Why stop? Can't form any common pair without characters from both strings.
Return: 0.
Why 0 and not something else? An empty string shares nothing with any string. The longest common subsequence between "" and anything is length 0.
j == len(text2): text2 is exhausted
Situation: No characters left in text2.
Why stop? Same reason. Need both strings to form a common subsequence.
Return: 0.
Symmetric: running out of either string ends the search. The answer can't grow without characters from both sides.
Why not return 1? Returning 1 would mean "I found a match," but we haven't. We're just out of characters. No match happened here.
Why not return -infinity? This isn't an "impossible" situation. It's a normal end. Running out of characters is expected.

12 What Smaller Problem Remains? (Transitions)

For each choice, what exactly changes and why?

MATCH: text1[i] == text2[j]
What did I just do? Matched one character. This character is part of the LCS.
What did I just gain? +1 to the LCS length. One character matched.
State changes:
i → i+1: text1[i] consumed. It matched. Move past it.

Why do both advance? A match consumes one character from each string. If only i advanced, text2[j] would still be available for a double-count. Both must move.
Remaining problem: 1 + lcs(i+1, j+1)
NO MATCH: text1[i] != text2[j]

Skip one character. Try both options, keep the better result.

Skip text1[i]
What did I just do? Decided text1[i] isn't useful right now. Passed over it.
What did I gain? Nothing. Skipping adds 0.

j stays: text2[j] wasn't consumed. It still needs a match from a later text1 character.
Call: lcs(i+1, j)

13 How Do We Combine the Results?

What exactly is the original question asking us to compute?

The problem says "longest." That means we want the maximum length. When I don't know which skip is better, I try both and keep whichever gives the larger result.

Match branch: adds +1 (I matched one character). Why +1? Each match contributes exactly one character to the length. Why not +2? I only matched one pair. Why not +0? I DID accomplish something: pairing two identical characters.
Skip branches: add +0 (no match, no gain). Why not +1? Skipping doesn't create a match. Nothing was paired. The skip branch adds nothing to the length.
Combining: max(skip_first, skip_second). Why max and not addition? I'm choosing ONE path, not combining two independent paths. Addition would be for counting all ways (like Distinct Subsequences). Here I want the single best path.
The pattern:
"Longest" → max().
"Count of ways" → +.
"Shortest / minimum cost" → min().
"Does any way exist?" → OR.

15 Brute-Force Code

def lcs_length(text1, text2, i, j):
    if i == len(text1) or j == len(text2):
        return 0

    if text1[i] == text2[j]:
        return 1 + lcs_length(text1, text2, i + 1, j + 1)

    skip_first = lcs_length(text1, text2, i + 1, j)
    skip_second = lcs_length(text1, text2, i, j + 1)
    return max(skip_first, skip_second)

How does a function with just (i, j) return the final answer?

Each call returns the LCS length for its remaining subproblem. lcs(2, 3) returns 0 (nothing left). lcs(1, 2) returns 1 (matched 'c'). lcs(1, 1) returns max(0, 1) = 1 (best skip).
lcs(0, 0) gets back 1 from its child, adds its own +1 for matching 'a', and returns 2. The answer builds from the bottom up through return values.

Where does repeated work appear?

Different decision paths can arrive at the same (i, j) pair. Trace the tree on "abcde" / "ace":

Different roads, same destination. Same state → same answer. Why compute it twice?

Without caching, the recursion tree has exponential branches. For strings of length m and n, it can be O(2^(m+n)) in the worst case. Each no-match call spawns TWO children, and the tree grows exponentially.

19 Memoization

Same state (i, j) always produces the same answer. Cache it.

Cache key: (i, j). The state. The minimum unique identifier.
Cache value: The LCS length for that state. An integer.
Total entries: At most m × n, where m = len(text1), n = len(text2).
def lcs_length(text1, text2, i, j, cache):
    if i == len(text1) or j == len(text2):
        return 0
    if (i, j) in cache:
        return cache[(i, j)]

    if text1[i] == text2[j]:
        result = 1 + lcs_length(text1, text2, i + 1, j + 1, cache)
    else:
        skip_first = lcs_length(text1, text2, i + 1, j, cache)
        skip_second = lcs_length(text1, text2, i, j + 1, cache)
        result = max(skip_first, skip_second)

    cache[(i, j)] = result
    return result
Teal: Cache lookup
Before computing, check if (i, j) was already solved. If yes, return immediately. This is what eliminates repeated work.
Teal: Cache store
After computing, save the result before returning. Future calls with the same (i, j) will hit the lookup.
What changed? Three lines added (lookup, store, pass cache). The recurrence is unchanged. The answer is unchanged. Only the runtime changed: from exponential to O(m × n).

20 Tabulation

Why the table dimensions come from the state

State = (i, j). Two state variables → two table dimensions. i ranges from 0 to len(text1). j ranges from 0 to len(text2). So the table is (len(text1)+1) × (len(text2)+1).

What does table[i][j] mean? The LCS length for text1[:i] and text2[:j]. (Note: tabulation uses prefix convention, not suffix. table[0][anything] = 0, because an empty prefix of text1 has no characters to match.)

Base cases become initialized cells

First row (i=0): empty text1 prefix. LCS = 0 for any text2 prefix.
First column (j=0): empty text2 prefix. LCS = 0 for any text1 prefix.
Both are already 0 from initialization.

Which cells does each transition depend on?

table[i-1][j-1] (diagonal, for match)
table[i-1][j] (up, for skip text1[i])
table[i][j-1] (left, for skip text2[j])

All three are above or to the left. So filling row by row, left to right guarantees every dependency has already been computed.

The code

def lcs_length(text1, text2):
    rows = len(text1)
    cols = len(text2)
    table = [[0] * (cols + 1) for _ in range(rows + 1)]

    for i in range(1, rows + 1):
        for j in range(1, cols + 1):
            if text1[i - 1] == text2[j - 1]:
                table[i][j] = table[i - 1][j - 1] + 1
            else:
                table[i][j] = max(table[i - 1][j], table[i][j - 1])

    return table[rows][cols]

All zeros. First row and column = base cases (empty prefix has LCS = 0). No separate initialization loop needed.
Brown: Iteration order
Row by row, left to right. Dependencies (up, left, diagonal) are always filled before the current cell.
Orange: Match → diagonal + 1
Same as recursion: match consumes both characters. In the table, "both consumed" means look diagonally (one row up, one column left).
Red: No match → max(up, left)

Purple: Return the answer

21 Space Optimization

Which previous states are actually needed?

Each cell uses three neighbors: table[i-1][j-1], table[i-1][j], table[i][j-1]. All from the current row or the row directly above. No cell ever looks at two rows back.

Keep only two rows: the previous row and the current row. After filling the current row, the previous row becomes the new "previous" and the old one is discarded. Space drops from O(m × n) to O(min(m, n)).
Does update direction matter? We fill left to right. curr_row[j-1] is already filled (left). prev_row[j] and prev_row[j-1] are from the previous row (already complete). No conflict. 
def lcs_length(text1, text2):
    if len(text2) > len(text1):
        text1, text2 = text2, text1
    cols = len(text2)
    prev_row = [0] * (cols + 1)
    curr_row = [0] * (cols + 1)

    for i in range(1, len(text1) + 1):
        for j in range(1, cols + 1):
            if text1[i - 1] == text2[j - 1]:
                curr_row[j] = prev_row[j - 1] + 1
            else:
                curr_row[j] = max(prev_row[j], curr_row[j - 1])
        prev_row, curr_row = curr_row, [0] * (cols + 1)

    return prev_row[cols]
What clarity is lost? We can no longer trace back through the full table to reconstruct the actual LCS string. Only the length is recoverable. If you need the subsequence itself, keep the full table.

22 Common Mistakes

Adding +1 on the skip branch
return 1 + lcs(i+1, j) ← WRONG
Skipping doesn't match anything. No character was paired. +0, not +1.
Detection: lcs("a", "b") returns 1 instead of 0.
Using addition instead of max on no-match
return lcs(i+1, j) + lcs(i, j+1) ← WRONG
Addition counts all paths. That's for "number of ways" problems (like Distinct Subsequences). Here we want the single longest, so max().
Detection: lcs("ab", "cd") returns a number greater than the shorter string's length.
Only advancing one pointer on match
return 1 + lcs(i+1, j) or return 1 + lcs(i, j+1) ← WRONG
A match consumes one from EACH string. If only i advances, text2[j] remains available and the same character gets matched again later. Double-counting.
Detection: lcs("a", "a") returns more than 1.
Returning 1 for the base case instead of 0
if i == len(text1): return 1 ← WRONG
Running out of characters isn't a success. It's the end. No match happened here. Return 0.
Detection: lcs("a", "b") returns 1 instead of 0.
Wrong table iteration order
Filling bottom-to-top or right-to-left with the standard recurrence. Each cell needs up, left, and diagonal. If the row above isn't filled yet, the values are wrong.
Detection: The table produces different results than the recursive solution on the same input.

    cols = len(word2)

def min_edits(word1, word2):

    prev_row = list(range(cols + 1))
    curr_row = [0] * (cols + 1)

1 What Is It Really Asking?

Pick characters from s1 and s2, one at a time, in each string's original order, to exactly reconstruct s3.

Allowed
Interleaving order between s1 and s2.
NOT allowed
Reordering characters within s1 or within s2.
Summary: Consume s1 and s2 left to right in any interleaving order and check whether the result matches s3 exactly.

2 What Would I Naturally Try?

Greedy instinct: walk s3 left to right, take from whichever string's next character matches.

s1="ab", s2="cd", s3="acbd"
Only one string ever matches at each step, so greedy gets True, but it's never actually tested against a tie.

3 Where Does That Fail?

s1="aax", s2="aay", s3="aayaax"
Greedy always prefers s1 on ties, uses up s1's "aa", then has no source for s3[2]='y'. Greedy says False.
Actual answer: True
Take all of s2 first, then all of s1: "aay" + "aax" = "aayaax" = s3.
The irreversible-decision trap: when s3's next character matches both s1[i] and s2[j], greedy must guess, and a wrong guess can strand later characters. Both paths must be tried, which means recursion.

4 What Decision Am I Stuck On?

Having consumed i characters from s1 and j from s2, s3 must have absorbed k = i + j characters so far.

s1
a a x
i is here. Everything before is consumed.
s2
a a y
j is here. Everything before is consumed.
What is preventing me from finishing?

s3[k] needs a source: s1[i] or s2[j]. If both match, which one actually supplied it?

5 What Can I Do?

If s1[i] == s3[i+j]: try can_interleave(i+1, j).
If s2[j] == s3[i+j]: try can_interleave(i, j+1).
If neither matches: dead end, return False.

Unlike LCS, there is no skipping. Every character of s3 must be accounted for by exactly one source, right now.

6 Why Only These Choices?

Skip s3[i+j] and come back later? No, s3 is built left to right, one character per step.
Source from deeper in s1 or s2? No, characters must be consumed strictly in order.
Take from both at once? No, one slot in s3 needs exactly one source.
Neither matches? Dead end, return False.
At most two branches, sometimes zero, never more than two.

count_ways(i, j) returns the number of distinct subsequences of source[i:] that equal target[j:].

Returns an integer count, not the subsequences. Original problem: count_ways(0, 0).

12 When Must We Stop?

j == len(target)
target fully matched. Return 1. Check this first.
i == len(source)
source exhausted, target remains. Return 0.

13 What Smaller Problem Remains?

CASE: source[i] == target[j] (Match)
USE: both advance → count_ways(i+1, j+1)
SKIP: only i advances, j waits → count_ways(i+1, j)
Combine: use + skip, both are distinct sets of positions.
CASE: source[i] != target[j] (No Match)
Only skip is legal → count_ways(i+1, j)

14 How Do We Combine Futures?

"Number of distinct subsequences" is a count, not a best-of. use and skip produce disjoint sets of ways, so combine with +, not max (max would undercount, like greedy).

The pattern: "longest/shortest" → max/min. "Number of ways" → +. "Does any way exist?" → OR.

19 Why Is It Slow?

Every match branches twice, so the call tree grows to 2^k, and many branches collide on the same (i, j), especially with repeated characters.

Same signal as every DP problem: a small, fixed-size state (i, j) revisited by exponentially many paths means overlapping subproblems, the cue to cache.

20 Memoization

def count_ways(source, target, i, j, cache):

TABLE MAPPING
table[i][j] = count_ways(i, j). table[i][len(target)] = 1. table[len(source)][j] = 0 for j < len(target).

Depends on row i+1, so rows fill bottom-up: from i = len(source) down to 0.

def count_ways(source, target):
    source_length = len(source)
    target_length = len(target)
    table = [[0] * (target_length + 1) for _ in range(source_length + 1)]

    for i in range(source_length + 1):
        table[i][target_length] = 1

    for i in range(source_length - 1, -1, -1):
        for j in range(target_length - 1, -1, -1):
            table[i][j] = table[i + 1][j]
            if source[i] == target[j]:
                table[i][j] += table[i + 1][j + 1]

    return table[0][0]

22 Space Optimization

Each cell only reads row i+1, so one row can be reused, updated in the right direction.

The subtle part: update j increasing, so row[j+1] still holds the old value when row[j] is written. Decreasing order would corrupt it. 
def count_ways(source, target):
    source_length = len(source)
    target_length = len(target)
    row = [0] * (target_length + 1)
    row[target_length] = 1

    for i in range(source_length - 1, -1, -1):
        for j in range(target_length):
            if source[i] == target[j]:
                row[j] += row[j + 1]

    return row[0]

source="aab", target="ab": [0,0,1] → [0,1,1] → [1,1,1] → [2,1,1]. Return 2. O(len(target)) space.

23 Common Mistakes

max instead of +: return max(use, skip) counts ways, not the best one. Detection: count_ways("aaa","a") returns 1 instead of 3.
Advancing target on mismatch: a mismatch only moves source, never target.
Swapped base cases: target matched = 1 (success), source exhausted = 0 (failure).
Missing skip on a match: the greedy failure from Step 4. Detection: count_ways("aab","ab") returns 1 instead of 2.
Wrong j direction in 1D: must go increasing, or row[j+1] gets corrupted.

24 Pattern Recognition

"Number of distinct ways" = counting, two strings = two dimensions, greedy fails on early commitment.
"Use then skip" and "skip then use" land on the same (i, j): overlapping subproblems.
Asymmetric roles, unlike LCS: source is negotiable, target is fixed. One-sided skipping.
When I see "count distinct ways" + subsequence with one fixed string, one negotiable string, I should consider one-sided-skip counting DP with addition.

When a star follows the pattern letter, the answer is TRUE if either skipping the pair works or consuming one text letter works. Otherwise the letters must match and both spots step forward.

1 The Problem

LEETCODE #10
Given a text and a pattern, decide whether the pattern matches the entire text. The pattern may contain . and *.
CharacterMeansExample
.any one character. Always exactly one, never zero.a.c matches abc

The star is never alone. It always belongs to the letter before it. Read a* as a single piece, not as an a followed by a *. Almost every bug in this problem comes from forgetting that.

Our running example throughout: text = "ab" and pattern = "a*b". The answer is TRUE.

2 Why We Cannot Just Walk Forward

Walking left to right and matching one character at a time works fine until a star appears. Then it stops being obvious, because the same pattern piece can swallow different amounts of text.

PatternTextHow many times a* was usedMatch?
a*bbzeroyes
a*babonceyes
a*baaabthree timesyes
The star does not know how many characters to take. A greedy rule ("take as many as possible") breaks on text = "aaa" with pattern = "a*a": if a* eats all three, nothing is left for the final a. So at every star we must be willing to try both: take none, or take one more.

3 The Question, And The Bookmark

Freeze partway through. We have matched some of the text against some of the pattern. What has to be written down so someone else could finish?

Only two things: how far into the text we are, and how far into the pattern we are. Nothing about how we got there matters, because whether the rest matches depends only on what is left.

matches_from(text_index, pattern_index)

answers TRUE or FALSE: does text from that spot onward match pattern from that spot onward?

Two spots, so the table is two dimensional. That is the same shape as Edit Distance and Interleaving String above, and for the same reason: two sequences being walked at once.

4 The Move

Everything depends on one question asked first: does a star come after the current pattern letter?

A STAR COMES NEXT

Two ways to succeed, and we only need one of them.

Use it zero times. Throw the pair away and jump the pattern forward by 2. The text does not move.

Use it once more. Only allowed if the current letters match. The text moves forward by 1 and the pattern stays put, so the star can be used again.

Either being TRUE makes the answer TRUE.

NO STAR

Only one way to succeed.

The current letters must match right now, either because they are equal or because the pattern has a . there.

If they match, step both spots forward by 1.

If they do not match, FALSE immediately.

Run that on our example. At text_index 0, pattern_index 0, the pattern is a and a star follows, so we try both branches:

BranchWhat is leftResult

use a* once moretext b against pattern a*bTRUE

One branch was enough, so the answer is TRUE.

The recursion stops when the pattern runs out. At that point the answer is TRUE only if the text ran out at the same moment.

7 The Code

def is_match(text, pattern):
    solved = {}

    # Does text[text_index:] match pattern[pattern_index:] ?
    def matches_from(text_index, pattern_index):
        if (text_index, pattern_index) in solved:
            return solved[(text_index, pattern_index)]

        if pattern_index == len(pattern):
            # pattern finished: only TRUE if the text finished too
            result = text_index == len(text)
        else:
            first_matches = (text_index < len(text)
                             and pattern[pattern_index] in (text[text_index], '.'))

            star_follows = (pattern_index + 1 < len(pattern)
                            and pattern[pattern_index + 1] == '*')

            if star_follows:
                result = (matches_from(text_index, pattern_index + 2)          # use it zero times
                          or (first_matches
                              and matches_from(text_index + 1, pattern_index)))  # use it once more
            else:
                result = (first_matches
                          and matches_from(text_index + 1, pattern_index + 1))

        solved[(text_index, pattern_index)] = result
        return result

    return matches_from(0, 0)
Reading the star line out loud

"Either the pair contributes nothing and I skip past it, or the current letter matches and I let the star eat it and try again with the same pattern spot."

Note that pattern_index does not advance in the second branch. That is what lets one star consume many characters. Advancing it there is the single most common way to break this.

Cost: there is one box per pair of spots, so len(text) × len(pattern) states, each doing constant work. That is O(n × m) time and space.
