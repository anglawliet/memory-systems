2D Table DP

Two sequences, one grid. Match on the diagonal, else take the best neighbor.

← Palindrome State Machine → Knapsack

The Problem

Longest Common Subsequence (LeetCode #1143)

Given two strings text1 and text2, return the length of their longest common subsequence.

text1
"abcde"
text2
"ace"
LCS = "ace", length = 3
text1 = "abc", text2 = "abc" → 3 Identical strings. Every character matches.
text1 = "abc", text2 = "def" → 0 No common characters at all.
text1 = "", text2 = "abc" → 0 Empty string. Nothing to match.
text1 = "a", text2 = "a" → 1 Single character, same in both.
text1 = "abcba", text2 = "abcbcba" → 5 text1 itself is a subsequence of text2.

1 What Is It Really Asking?

What does "subsequence" mean?

A subsequence keeps the original order but can skip characters. It does NOT need to be contiguous.

Valid subsequences of "abcde"
"ace" (skip b,d) ✓
"abcde" (skip nothing) ✓
"a" (skip b,c,d,e) ✓
"" (skip everything) ✓
NOT subsequences of "abcde"
"aec" (e comes before c in result, but after c in original) ✗
"ba" (b comes before a in result, but after a in original) ✗

What does "common" mean?

A common subsequence must be a subsequence of BOTH strings. Not just one.

Example: text1 = "abcde", text2 = "ace".
"ace" is a subsequence of text1 (skip b,d). "ace" is a subsequence of text2 (skip nothing). So "ace" is a common subsequence.
"abd" is a subsequence of text1, but NOT of text2 (text2 has no 'b' or 'd'). Not common.

What does "longest" mean?

There might be many common subsequences. We want the one with the maximum length. We return the length, not the subsequence itself.

Summary: Find the maximum number of characters I can pick from both strings such that the picked characters appear in the same order in both strings.

2 What Would I Naturally Try?

The greedy instinct

Most beginners think: "Walk through text1 left to right. For each character, grab its first available match in text2."

GREEDY ON THE EASY CASE: text1 = "abcde", text2 = "ace"
text1[0] = 'a'. Scan text2 for 'a' → found at text2[0]. Match!
text1[1] = 'b'. Scan text2 after index 0 → 'c', 'e'. No 'b'. Skip.
text1[2] = 'c'. Scan text2 after index 0 → text2[1] = 'c'. Match!
text1[3] = 'd'. Scan text2 after index 1 → 'e'. No 'd'. Skip.
text1[4] = 'e'. Scan text2 after index 1 → text2[2] = 'e'. Match!
Greedy result: "ace", length 3. Correct!

Greedy works here. It feels right. But now try a different input:

3 Where Does That Fail?

GREEDY FAILS: text1 = "cab", text2 = "abc"
text1[0] = 'c'. Scan text2 for 'c' → found at text2[2]. Match! (j moves to 3)
text1[1] = 'a'. Scan text2 after index 2 → nothing left. Skip.
text1[2] = 'b'. Scan text2 after index 2 → nothing left. Skip.
Greedy result: "c", length 1.
But the actual LCS = "ab", length 2!
text1 has 'a' at index 1, 'b' at index 2. text2 has 'a' at index 0, 'b' at index 1. In order in both strings. "ab" is a common subsequence of length 2.

What went wrong?

Greedy grabbed 'c' at position 2 in text2, consuming the entire remaining string. That was an irreversible decision. It didn't consider that skipping 'c' would leave room for the longer match "ab".

The irreversible-decision trap: Greedy picks the first match it finds and moves on. But sometimes the best move is to skip a valid match, because a different combination of matches later gives a longer result. We can't know which choices lead to the longest result without trying multiple paths.

Why brute force becomes necessary

Since we can't commit to one match greedily, we need to explore: "What if I take this match? What if I skip it?" For every matching pair, both options might lead to different outcomes. That means branching, which means recursion.

4 What Decision Am I Stuck On?

Freeze inside one recursive call

Imagine I'm at position i in text1 and position j in text2. I see two characters: text1[i] and text2[j].

text1
a b c d e
i is here. Everything before is decided.
text2
a c e
j is here. Everything before is decided.
What is preventing me from finishing?

I need to decide: what do I do with these two characters? The answer depends on whether they're the same or not. That's the most natural first check when comparing two sequences: do these two characters match?

5 What Can I Do With These Two Characters?

Case 1: They match

If text1[i] == text2[j], this pair could be part of the LCS. Should I always take it?

Is there ever a reason to skip a match? No. Taking a match gives +1. Skipping it gives +0 at best. A free match is always worth taking. (This is different from Distinct Subsequences, where skipping a match can lead to more total counts. Here we're maximizing length, so a guaranteed +1 is always optimal.)

Match: Take it. Both characters consumed. +1 to the LCS. Move to lcs(i+1, j+1).

Case 2: They don't match

If text1[i] != text2[j], at least one character is useless right now. Which one should I skip? I don't know.

Two options:

Skip text1[i]: Maybe it doesn't match anything useful in text2. Move to lcs(i+1, j).
Skip text2[j]: Maybe it doesn't match anything useful in text1. Move to lcs(i, j+1).

I don't know which is better. Try both, keep the better result.

6 Why Only These Choices?

Test every idea a beginner might have

Can I skip both characters at once?
No. Skipping both throws away a character that might match something later. Maybe text1[i] matches a future text2 character, or vice versa. Skipping both is always ≤ skipping just one. It's wasteful.
Can I take a non-matching pair?
No. A common subsequence requires the same character at each position. A mismatched pair contributes nothing.
Can I jump ahead to find a match instead of skipping one at a time?
That's what the recursion does. By skipping text1[i], the next call tries text1[i+1] against text2[j]. Then text1[i+2], and so on. Each skip-one-at-a-time call explores all future matches. Jumping ahead is just multiple skips.
Can I use text1[i] to match a different character in text2 (not text2[j])?
Yes, and the recursion handles it. When I skip text2[j], the next call compares text1[i] against text2[j+1]. If that matches, great. If not, it skips again. Every possible pairing is explored.
After eliminating everything illegal:
Match? Take it. One branch. No choice needed.
No match? Skip text1[i] OR skip text2[j]. Two branches. Take the max.

10 What Does the Function Promise?

Before writing a single line, state the contract in English

lcs(i, j) returns the length of the longest common subsequence of text1[i:] and text2[j:].
What has already been decided? Everything before i in text1 and before j in text2. Those decisions are done. This function doesn't see them.
What remains available? text1[i:] and text2[j:]. All characters from i onward and from j onward.
What type of value is returned? An integer: the length (count of characters), not the subsequence itself.
The original problem: lcs(0, 0). "LCS of the full text1 and full text2."
Why does this matter? Every recursive call must preserve this promise. If I call lcs(i+1, j), it must really answer "LCS of text1[i+1:] and text2[j:]." If it doesn't, the recursion is broken.

11 When Must We Stop? (Base Cases)

If I keep making decisions, when must I eventually stop?

Don't look at the recurrence to find base cases. Ask: "What situation makes the answer trivially obvious?"

i == len(text1): text1 is exhausted
Situation: No characters left in text1.
Why stop? Can't form any common pair without characters from both strings.
Return: 0.
Why 0 and not something else? An empty string shares nothing with any string. The longest common subsequence between "" and anything is length 0.
j == len(text2): text2 is exhausted
Situation: No characters left in text2.
Why stop? Same reason. Need both strings to form a common subsequence.
Return: 0.
Symmetric: running out of either string ends the search. The answer can't grow without characters from both sides.
Why not return 1? Returning 1 would mean "I found a match," but we haven't. We're just out of characters. No match happened here.
Why not return -infinity? This isn't an "impossible" situation. It's a normal end. Running out of characters is expected.

12 What Smaller Problem Remains? (Transitions)

For each choice, what exactly changes and why?

MATCH: text1[i] == text2[j]
What did I just do? Matched one character. This character is part of the LCS.
What did I just gain? +1 to the LCS length. One character matched.
State changes:
i → i+1: text1[i] consumed. It matched. Move past it.
j → j+1: text2[j] consumed. Same character, same match. Move past it.
Why do both advance? A match consumes one character from each string. If only i advanced, text2[j] would still be available for a double-count. Both must move.
Remaining problem: 1 + lcs(i+1, j+1)
NO MATCH: text1[i] != text2[j]

Skip one character. Try both options, keep the better result.

Skip text1[i]
What did I just do? Decided text1[i] isn't useful right now. Passed over it.
What did I gain? Nothing. Skipping adds 0.
i → i+1: Skipped past text1[i].
j stays: text2[j] wasn't consumed. It still needs a match from a later text1 character.
Call: lcs(i+1, j)
Skip text2[j]
What did I just do? Decided text2[j] isn't useful right now. Passed over it.
What did I gain? Nothing. Skipping adds 0.
i stays: text1[i] wasn't consumed. It might match a later text2 character.
j → j+1: Skipped past text2[j].
Call: lcs(i, j+1)

13 How Do We Combine the Results?

What exactly is the original question asking us to compute?

The problem says "longest." That means we want the maximum length. When I don't know which skip is better, I try both and keep whichever gives the larger result.

Match branch: adds +1 (I matched one character). Why +1? Each match contributes exactly one character to the length. Why not +2? I only matched one pair. Why not +0? I DID accomplish something: pairing two identical characters.
Skip branches: add +0 (no match, no gain). Why not +1? Skipping doesn't create a match. Nothing was paired. The skip branch adds nothing to the length.
Combining: max(skip_first, skip_second). Why max and not addition? I'm choosing ONE path, not combining two independent paths. Addition would be for counting all ways (like Distinct Subsequences). Here I want the single best path.
The pattern:
"Longest" → max().
"Count of ways" → +.
"Shortest / minimum cost" → min().
"Does any way exist?" → OR.

Now it writes itself

Every branch has already been justified. The recurrence is just a compact summary:

15 Brute-Force Code

def lcs_length(text1, text2, i, j):
    if i == len(text1) or j == len(text2):
        return 0

    if text1[i] == text2[j]:
        return 1 + lcs_length(text1, text2, i + 1, j + 1)

    skip_first = lcs_length(text1, text2, i + 1, j)
    skip_second = lcs_length(text1, text2, i, j + 1)
    return max(skip_first, skip_second)

Does every call preserve the promise?

lcs(i+1, j+1): "LCS of text1[i+1:] and text2[j+1:]." ✓ Both characters consumed.
lcs(i+1, j): "LCS of text1[i+1:] and text2[j:]." ✓ Skipped text1[i].
lcs(i, j+1): "LCS of text1[i:] and text2[j+1:]." ✓ Skipped text2[j].

Follow one example through every call and return

How does a function with just (i, j) return the final answer?

Each call returns the LCS length for its remaining subproblem. lcs(2, 3) returns 0 (nothing left). lcs(1, 2) returns 1 (matched 'c'). lcs(1, 1) returns max(0, 1) = 1 (best skip).
lcs(0, 0) gets back 1 from its child, adds its own +1 for matching 'a', and returns 2. The answer builds from the bottom up through return values.

18 Why Is It Slow?

Where does repeated work appear?

Different decision paths can arrive at the same (i, j) pair. Trace the tree on "abcde" / "ace":

lcs("abcde", "ace", 0, 0)
  'a'=='a' MATCH: 1 + lcs(1, 1)
    'b'!='c': max(lcs(2,1), lcs(1,2))
      lcs(2, 1)                  +
        'c'=='c' MATCH           |
      lcs(1, 2)                  |
        'b'!='e': max(           |
          lcs(2, 2)        ------+ BOTH paths
          lcs(1, 3)=0)           | reach (2,2)!
                                 +
lcs(2, 2) computed from two different skip paths
Different roads, same destination. Same state → same answer. Why compute it twice?

Without caching, the recursion tree has exponential branches. For strings of length m and n, it can be O(2^(m+n)) in the worst case. Each no-match call spawns TWO children, and the tree grows exponentially.

19 Memoization

Same state (i, j) always produces the same answer. Cache it.

Cache key: (i, j). The state. The minimum unique identifier.
Cache value: The LCS length for that state. An integer.
Total entries: At most m × n, where m = len(text1), n = len(text2).
def lcs_length(text1, text2, i, j, cache):
    if i == len(text1) or j == len(text2):
        return 0
    if (i, j) in cache:
        return cache[(i, j)]

    if text1[i] == text2[j]:
        result = 1 + lcs_length(text1, text2, i + 1, j + 1, cache)
    else:
        skip_first = lcs_length(text1, text2, i + 1, j, cache)
        skip_second = lcs_length(text1, text2, i, j + 1, cache)
        result = max(skip_first, skip_second)

    cache[(i, j)] = result
    return result
Teal: Cache lookup
Before computing, check if (i, j) was already solved. If yes, return immediately. This is what eliminates repeated work.
Teal: Cache store
After computing, save the result before returning. Future calls with the same (i, j) will hit the lookup.
What changed? Three lines added (lookup, store, pass cache). The recurrence is unchanged. The answer is unchanged. Only the runtime changed: from exponential to O(m × n).

20 Tabulation

Why the table dimensions come from the state

State = (i, j). Two state variables → two table dimensions. i ranges from 0 to len(text1). j ranges from 0 to len(text2). So the table is (len(text1)+1) × (len(text2)+1).

What does table[i][j] mean? The LCS length for text1[:i] and text2[:j]. (Note: tabulation uses prefix convention, not suffix. table[0][anything] = 0, because an empty prefix of text1 has no characters to match.)

Base cases become initialized cells

First row (i=0): empty text1 prefix. LCS = 0 for any text2 prefix.
First column (j=0): empty text2 prefix. LCS = 0 for any text1 prefix.
Both are already 0 from initialization.

Which cells does each transition depend on?

table[i-1][j-1] (diagonal, for match)
table[i-1][j] (up, for skip text1[i])
table[i][j-1] (left, for skip text2[j])

All three are above or to the left. So filling row by row, left to right guarantees every dependency has already been computed.

Gold cells = matches (came from diagonal + 1). Bottom-right = answer: 3.

MATCH
table[i][j] = table[i-1][j-1] + 1

NO MATCH
table[i][j] = max(table[i-1][j], table[i][j-1])

Walking through one row

Row "c" (i=2): text1[1] = 'c'.

j=1 (text2[0]='a'): 'c' != 'a'. max(table[1][1], table[2][0]) = max(1, 0) = 1.
j=2 (text2[1]='b'): 'c' != 'b'. max(table[1][2], table[2][1]) = max(1, 1) = 1.
j=3 (text2[2]='c'): 'c' == 'c'. Match! table[1][2] + 1 = 1 + 1 = 2.
j=4 (text2[3]='d'): 'c' != 'd'. max(table[1][4], table[2][3]) = max(1, 2) = 2.
j=5 (text2[4]='e'): 'c' != 'e'. max(table[1][5], table[2][4]) = max(1, 2) = 2.

The code

def lcs_length(text1, text2):
    rows = len(text1)
    cols = len(text2)
    table = [[0] * (cols + 1) for _ in range(rows + 1)]

    for i in range(1, rows + 1):
        for j in range(1, cols + 1):
            if text1[i - 1] == text2[j - 1]:
                table[i][j] = table[i - 1][j - 1] + 1
            else:
                table[i][j] = max(table[i - 1][j], table[i][j - 1])

    return table[rows][cols]
Pink: Table initialization
All zeros. First row and column = base cases (empty prefix has LCS = 0). No separate initialization loop needed.
Brown: Iteration order
Row by row, left to right. Dependencies (up, left, diagonal) are always filled before the current cell.
Orange: Match → diagonal + 1
Same as recursion: match consumes both characters. In the table, "both consumed" means look diagonally (one row up, one column left).
Red: No match → max(up, left)
Same as recursion: try both skips. In the table, "skip text1[i]" = look up (shorter text1 prefix). "Skip text2[j]" = look left (shorter text2 prefix).
Purple: Return the answer
Bottom-right corner: full text1 prefix, full text2 prefix. The answer to the original problem.

21 Space Optimization

Which previous states are actually needed?

Each cell uses three neighbors: table[i-1][j-1], table[i-1][j], table[i][j-1]. All from the current row or the row directly above. No cell ever looks at two rows back.

Keep only two rows: the previous row and the current row. After filling the current row, the previous row becomes the new "previous" and the old one is discarded. Space drops from O(m × n) to O(min(m, n)).
Does update direction matter? We fill left to right. curr_row[j-1] is already filled (left). prev_row[j] and prev_row[j-1] are from the previous row (already complete). No conflict. 
def lcs_length(text1, text2):
    if len(text2) > len(text1):
        text1, text2 = text2, text1
    cols = len(text2)
    prev_row = [0] * (cols + 1)
    curr_row = [0] * (cols + 1)

    for i in range(1, len(text1) + 1):
        for j in range(1, cols + 1):
            if text1[i - 1] == text2[j - 1]:
                curr_row[j] = prev_row[j - 1] + 1
            else:
                curr_row[j] = max(prev_row[j], curr_row[j - 1])
        prev_row, curr_row = curr_row, [0] * (cols + 1)

    return prev_row[cols]
What clarity is lost? We can no longer trace back through the full table to reconstruct the actual LCS string. Only the length is recoverable. If you need the subsequence itself, keep the full table.

22 Common Mistakes

Adding +1 on the skip branch
return 1 + lcs(i+1, j) ← WRONG
Skipping doesn't match anything. No character was paired. +0, not +1.
Detection: lcs("a", "b") returns 1 instead of 0.
Using addition instead of max on no-match
return lcs(i+1, j) + lcs(i, j+1) ← WRONG
Addition counts all paths. That's for "number of ways" problems (like Distinct Subsequences). Here we want the single longest, so max().
Detection: lcs("ab", "cd") returns a number greater than the shorter string's length.
Only advancing one pointer on match
return 1 + lcs(i+1, j) or return 1 + lcs(i, j+1) ← WRONG
A match consumes one from EACH string. If only i advances, text2[j] remains available and the same character gets matched again later. Double-counting.
Detection: lcs("a", "a") returns more than 1.
Returning 1 for the base case instead of 0
if i == len(text1): return 1 ← WRONG
Running out of characters isn't a success. It's the end. No match happened here. Return 0.
Detection: lcs("a", "b") returns 1 instead of 0.
Wrong table iteration order
Filling bottom-to-top or right-to-left with the standard recurrence. Each cell needs up, left, and diagonal. If the row above isn't filled yet, the values are wrong.
Detection: The table produces different results than the recursive solution on the same input.
Off-by-one in tabulation indices
text1[i] == text2[j] in the tabulation loop ← WRONG
Tabulation uses 1-indexed table but 0-indexed strings. The correct comparison is text1[i-1] == text2[j-1].
Detection: Index out of bounds when i equals len(text1).

23 Pattern Recognition

What clues suggested DP?
"Longest" = optimization. Two strings = two dimensions. Greedy fails because decisions interact. Different decision paths converge on the same state.
What uncertainty forced branching?
On a mismatch, I don't know which character to skip. That uncertainty creates two branches.
What caused overlapping subproblems?
Skipping text1[i] then text2[j] and skipping text2[j] then text1[i] both reach lcs(i+1, j+1). Different paths, same destination.
Which operator follows from the question wording?
"Longest" → max(). "Count of ways" would mean addition. "Shortest" would mean min().
When I see _______, I should consider _______:
When I see "two strings" + "order matters" + "optimize", I should consider two-pointer DP with match/skip logic.
What generalizes?
Any time I have two sequences and I'm comparing elements pairwise, the structure is: match (diagonal) or skip one (up or left). The only things that change across problems are: what happens on a match (+1 for LCS, +0 for edit distance, use+skip for distinct subsequences), what the combining operation is (max, min, add), and what the base cases are.

1 Unique Paths

▶
LEETCODE #62
A robot starts at the top-left of an m x n grid. It can only move down or right. Count the number of unique paths to the bottom-right corner.
Example:
m = 3, n = 3 (a 3x3 grid)

start→→ ↓↓ →→end


One path: right, right, down, down. Another: down, right, down, right.
Answer: 6 unique paths total.
m = 2, n = 2 → 2 — Right then down, or down then right. Simplest case.
m = 1, n = 5 → 1 — Single row. Only one path: all right.
THE KEY IDEA
No match/no-match here. Every cell gets its value from exactly two neighbors: the cell above and the cell to the left. table[r][c] = table[r-1][c] + table[r][c-1]. First row and first column are all 1's (only one way to get there).

Why each variable changes

Move DOWN
Action: Robot moves one cell down.
Immediate reward: +0. Moving doesn't add paths, it's one step toward the destination.
State changes:
r → r+1: Moved down one row.
c stays the same: Didn't move horizontally.
Call: count_paths(r+1, c)
Why doesn't c change? Moving down is purely vertical. The column position is unchanged.
Move RIGHT
Action: Robot moves one cell right.
Immediate reward: +0. Just another step toward the destination.
State changes:
r stays the same: Didn't move vertically.
c → c+1: Moved right one column.
Call: count_paths(r, c+1)
Why doesn't r change? Moving right is purely horizontal. The row position is unchanged.
Final decision: result = down + right. We count all paths, so we add the counts from both directions.

Recursion

def count_paths(rows, cols, r, c, cache):
    if r == rows - 1 and c == cols - 1:
        return 1
    if r >= rows or c >= cols:
        return 0
    if (r, c) in cache:
        return cache[(r, c)]

    go_down = count_paths(rows, cols, r + 1, c, cache)
    go_right = count_paths(rows, cols, r, c + 1, cache)
    cache[(r, c)] = go_down + go_right
    return cache[(r, c)]

Tabulation

def count_paths(rows, cols):
    table = [[1] * cols for _ in range(rows)]

    for r in range(1, rows):
        for c in range(1, cols):
            table[r][c] = table[r - 1][c] + table[r][c - 1]

    return table[rows - 1][cols - 1]
Simplest 2D table: no conditions, just add up + left. First row and first column all 1's (one straight-line path). Pascal's triangle rotated.

2 Edit Distance

▶
LEETCODE #72
Given two words, find the minimum number of operations (insert, delete, replace) to transform word1 into word2.
Example:
word1 = "horse", word2 = "ros"

replace h with r → "rorse"
delete r → "rorse" → "rose"
delete e → "rose" → "ros"

Answer: 3 operations (one replace, two deletes).
word1 = "abc", word2 = "abc" → 0 — Same string. No edits needed.
word1 = "intention", word2 = "execution" → 5 — 3 replaces, 1 delete, 1 insert.

What do I need to know?

THE STATE
min_edits(i, j) = minimum operations to transform word1[i:] into word2[j:].

i = how far we've processed in word1. Characters word1[0..i-1] are already handled.
j = how far we've processed in word2. Characters word2[0..j-1] are already produced.

The choices at state (i, j)

We're looking at word1[i] and word2[j]. Either they match or they don't.

CASE: word1[i] == word2[j] (Match)
Action: Characters already match. No operation needed. Move past both.
Immediate cost: +0. A match is free because the character is already correct.
State changes:
i → i+1: We consumed word1[i]. It matched, so it's handled.
j → j+1: We produced word2[j]. The match covers it.
Remaining subproblem: Transform word1[i+1:] into word2[j+1:].
Call: min_edits(i+1, j+1)
Why not (i+1, j) or (i, j+1)? Both characters are dealt with. Advancing only one would leave a character unmatched that we already know matches.
CASE: word1[i] != word2[j] (No Match)

Three operations. Each has cost 1. Each changes the state differently.

Operation 1: REPLACE word1[i] with word2[j]
Action: Overwrite word1[i] so it becomes word2[j].
Immediate cost: +1. One replace operation used.
State changes:
i → i+1: word1[i] is now correct (we replaced it). Move past it.
j → j+1: word2[j] is now produced (by the replacement). Move past it.
Remaining subproblem: Transform word1[i+1:] into word2[j+1:].
Call: 1 + min_edits(i+1, j+1)
Why both advance? Replace handles both positions at once: it consumes word1[i] and produces word2[j] in a single operation.
Operation 2: DELETE word1[i]
Action: Remove word1[i] from word1. It doesn't correspond to anything in word2.
Immediate cost: +1. One delete operation used.
State changes:
i → i+1: word1[i] is deleted, so we move past it.
j stays the same: We haven't produced any character of word2 yet. word2[j] still needs to be handled.
Remaining subproblem: Transform word1[i+1:] into word2[j:]. (Same j, word2 hasn't progressed.)
Call: 1 + min_edits(i+1, j)
Why doesn't j change? Deleting from word1 doesn't produce anything in word2. The target character word2[j] is still waiting.
Operation 3: INSERT word2[j] before word1[i]
Action: Insert the character word2[j] into word1 at position i. This produces the needed character.
Immediate cost: +1. One insert operation used.
State changes:
i stays the same: We didn't consume any character from word1. word1[i] is still there, waiting to be dealt with.
j → j+1: We produced word2[j] (by inserting it). Move past it.
Remaining subproblem: Transform word1[i:] into word2[j+1:]. (Same i, word1 hasn't progressed.)
Call: 1 + min_edits(i, j+1)
Why doesn't i change? Inserting adds a new character. It doesn't consume word1[i]. That character still needs to be matched, replaced, or deleted later.
Final decision: result = min(replace, delete, insert). We want the cheapest path.

Base cases (derived from the state)

i == len(word1)
Situation: We've consumed all of word1, but word2[j:] still has characters left.
Only option: Insert every remaining character of word2.
Cost: len(word2) - j (one insert per remaining character).
This is NOT 0 like LCS. There's still work to do.
j == len(word2)
Situation: We've produced all of word2, but word1[i:] still has characters left.
Only option: Delete every remaining character of word1.
Cost: len(word1) - i (one delete per remaining character).
Extra word1 characters are baggage. They must go.

Recursion (with memoization)

def min_edits(word1, word2, i, j, cache):
    if i == len(word1):
        return len(word2) - j
    if j == len(word2):
        return len(word1) - i
    if (i, j) in cache:
        return cache[(i, j)]

    if word1[i] == word2[j]:
        result = min_edits(word1, word2, i + 1, j + 1, cache)
    else:
        replace = 1 + min_edits(word1, word2, i + 1, j + 1, cache)
        delete = 1 + min_edits(word1, word2, i + 1, j, cache)
        insert = 1 + min_edits(word1, word2, i, j + 1, cache)
        result = min(replace, delete, insert)

    cache[(i, j)] = result
    return result

Tabulation

TABLE MAPPING
Row i = how much of word1 we've processed (0 to len(word1)).
Col j = how much of word2 we've produced (0 to len(word2)).
table[i][j] = min operations to transform word1[i:] into word2[j:].

Edges: table[i][0] = i (delete all remaining word1). table[0][j] = j (insert all remaining word2).
These are the base cases, written directly into the first row and column. 
def min_edits(word1, word2):
    rows = len(word1)
    cols = len(word2)
    table = [[0] * (cols + 1) for _ in range(rows + 1)]

    for i in range(rows + 1):
        table[i][0] = i
    for j in range(cols + 1):
        table[0][j] = j

    for i in range(1, rows + 1):
        for j in range(1, cols + 1):
            if word1[i - 1] == word2[j - 1]:
                table[i][j] = table[i - 1][j - 1]
            else:
                table[i][j] = 1 + min(
                    table[i - 1][j - 1],
                    table[i - 1][j],
                    table[i][j - 1]
                )

    return table[rows][cols]

LCS vs Edit Distance: same grid, different goal

LCS (parent)
Match: diagonal + 1 (count it!)
No match: max(up, left)
Goal: maximize matches
Base case: 0 (nothing to match)
2 choices on mismatch
Edit Distance
Match: diagonal + 0 (free!)
No match: 1 + min(diag, up, left)
Goal: minimize operations
Base case: remaining length
3 choices on mismatch
Why the directions map to operations:
Diagonal (i+1, j+1) = replace. Both pointers advance because replace handles both positions.
Up (i+1, j) = delete. Only i advances because we removed from word1, word2 hasn't progressed.
Left (i, j+1) = insert. Only j advances because we added to word2's production, word1 hasn't been consumed.

3 Interleaving String

▶
LEETCODE #97
Given strings s1, s2, and s3, check if s3 can be formed by interleaving s1 and s2 while keeping their character order.
Example:
s1 = "aab", s2 = "axy", s3 = "aaxaby"

Interleave: aaxaby (s1 chars, s2 chars)
Both strings keep their original order. Answer: True.

s1 = "ab", s2 = "cd", s3 = "acdb" → True (acdb)
s1 = "ab", s2 = "cd", s3 = "abdc" → True (abdc)
Not allowed: rearranging characters within s1 or s2. Only the interleaving order changes.

Why not just greedy?

If only one string matches the next character in s3, you pick it. But when both s1[i] and s2[j] match, picking the wrong one leads to a dead end. You need to try both paths.

THE KEY IDEA
table[i][j] = True if s3[:i+j] can be formed from s1[:i] and s2[:j]. At each cell, the next character in s3 is s3[i+j-1]. It came from either s1 (above) or s2 (left).

Why each variable changes

State: can_interleave(i, j). We need to produce s3[i+j] next. It must come from either s1[i] or s2[j].

Take from s1 (when s1[i] == s3[i+j])
Action: Use s1[i] to produce s3[i+j].
State changes:
i → i+1: s1[i] consumed. It produced the next character of s3.
j stays the same: s2[j] not used. Still available.
Call: can_interleave(i+1, j)
Why doesn't j change? We took from s1, not s2. s2[j] is still the next available character from s2.
Take from s2 (when s2[j] == s3[i+j])
Action: Use s2[j] to produce s3[i+j].
State changes:
i stays the same: s1[i] not used. Still available.
j → j+1: s2[j] consumed. It produced the next character of s3.
Call: can_interleave(i, j+1)
Why doesn't i change? We took from s2, not s1. s1[i] is still available.
Decision: If either path returns True, the interleaving works. OR logic, not max/min.

Recursion

def can_interleave(s1, s2, s3, i, j, cache):
    if i + j == len(s3):
        return i == len(s1) and j == len(s2)
    if (i, j) in cache:
        return cache[(i, j)]

    result = False
    if i < len(s1) and s1[i] == s3[i + j]:
        result = can_interleave(s1, s2, s3, i + 1, j, cache)
    if not result and j < len(s2) and s2[j] == s3[i + j]:
        result = can_interleave(s1, s2, s3, i, j + 1, cache)

    cache[(i, j)] = result
    return result

Tabulation

def can_interleave(s1, s2, s3):
    if len(s1) + len(s2) != len(s3):
        return False

    rows = len(s1)
    cols = len(s2)
    table = [[False] * (cols + 1) for _ in range(rows + 1)]
    table[0][0] = True

    for j in range(1, cols + 1):
        table[0][j] = table[0][j - 1] and s2[j - 1] == s3[j - 1]

    for i in range(1, rows + 1):
        table[i][0] = table[i - 1][0] and s1[i - 1] == s3[i - 1]

    for i in range(1, rows + 1):
        for j in range(1, cols + 1):
            from_s1 = table[i - 1][j] and s1[i - 1] == s3[i + j - 1]
            from_s2 = table[i][j - 1] and s2[j - 1] == s3[i + j - 1]
            table[i][j] = from_s1 or from_s2

    return table[rows][cols]
The twist: no "match" in the LCS sense. Instead, check if the next char in s3 came from s1 (look up) or s2 (look left). Boolean cells instead of counts.

4 Distinct Subsequences

▶
LEETCODE #115
Given strings s and t, count how many distinct subsequences of s equal t.
Example:
s = "rabbbit", t = "rabbit"

s has three b's. To spell "rabbit" you need two b's. Which two do you pick?
Way 1: rab1b2it
Way 2: rab1_b3it
Way 3: ra_b2b3it

Answer: 3 distinct subsequences.
You're not rearranging anything. You're choosing which characters in s to "use" to form t, keeping the order.
s = "babgbag", t = "bag" → 5 — 3 b's, 2 a's, 2 g's. Five ways to spell "bag".
s = "aabb", t = "ab" → 4 — 2 a's × 2 b's = 4 ways to pick one of each.
CLASSIFICATION
What does it compute? Count the number of ways to form one string from another by choosing characters.
Why not greedy? Greedy picks the first matching character. But we need ALL ways, not just one. Skipping a match now might lead to more total subsequences through later duplicates.
Which family? 2D table (two strings, one grid). Same grid as LCS, but counting paths instead of maximizing length.
RECURSIVE QUESTION
"In how many ways can I form t[j:] using characters from s[i:]?"

Plain English first: I'm looking at position i in s and position j in t. How many different ways can I pick characters from s (starting at i) that spell out the rest of t (starting at j)?

When must I stop?

Before thinking about choices, ask: "When is the answer obvious without any recursion?"

j == len(t): all of t is matched
Situation: I've matched every character of t. Nothing left to spell.
Why stop? The target string is fully formed. No more work to do.
Return: 1. This IS one valid subsequence. I found a complete way.
NOT 0. Reaching the end means success, so count it as one way.
i == len(s): ran out of s characters
Situation: I've exhausted s, but t[j:] still has unmatched characters.
Why stop? No more characters in s to pick from. Can't finish spelling t.
Return: 0. No way to complete the match.
Order matters: check j == len(t) FIRST. If both exhausted, the answer is 1 (success), not 0.
CHOICES (DISCOVERED, NOT LISTED)
Situation: I'm at s[i] and I need to match t[j] next.
The natural first question: Does s[i] match t[j]?

If they match: I have a real choice. I can USE s[i] to cover t[j], or I can SKIP it (maybe a later copy of this character leads to more subsequences). Both are valid, so I count both and add.
If they don't match: s[i] can't help with t[j]. Only option is to skip it.

Why is "use + skip" the key insight? In LCS, a match is always taken (no reason to skip a free match when maximizing). Here I'm COUNTING all ways. Even when characters match, skipping can lead to different valid subsequences through later duplicates. Both paths contribute to the total count.

Why can't I skip t[j]? t is the target. Every character of t must be matched. Skipping a character of t would change what I'm trying to spell. I can only skip characters of s (choosing which copies to use).

Why each variable changes

CASE: s[i] == t[j] (Match)

Two options. Characters match, but I can USE this match or SKIP it. Count both paths (add them).

Option 1: USE s[i] to match t[j]
Action: Use s[i] to match t[j]. Both characters consumed.
State changes:
i → i+1: s[i] consumed (used for the match). Move past it.
j → j+1: t[j] matched. Move to the next target character.
Call: count_subsequences(i+1, j+1)
Why both advance? Using s[i] to match t[j] consumes one character from each string. Both positions are handled.
Option 2: SKIP s[i] (even though it matches)
Action: Skip s[i]. Maybe a later copy of this character leads to more subsequences.
State changes:
i → i+1: s[i] skipped. Move past it.
j stays the same: t[j] not matched yet. Still needs to be covered by a later character.
Call: count_subsequences(i+1, j)
Why doesn't j change? I chose not to use this match. t[j] still needs to be matched by a later s character.
Decision: result = use + skip. Counting all distinct subsequences, so ADD both paths.
CASE: s[i] != t[j] (No Match)
Action: s[i] can't match t[j]. Only option: skip it.
State changes:
i → i+1: s[i] skipped (useless for current target).
j stays the same: t[j] still waiting to be matched.
Call: count_subsequences(i+1, j)

Watch it play out

Trace s="rabbbit", t="rabbit", starting at i=0, j=0:

i=0, j=0: s[0]='r' == t[0]='r'. Match! Use it (i=1, j=1) + skip it (i=1, j=0). Follow the "use" path:
i=1, j=1: s[1]='a' == t[1]='a'. Match! Use it. Now i=2, j=2.
i=2, j=2: s[2]='b' == t[2]='b'. Match! Here's where it branches:
USE b1: count_subsequences(3, 3) (used first b)
SKIP b1: count_subsequences(3, 2) (save for later b's)
The branching at b's is exactly why there are 3 ways. Three b's, need two, and C(3,2) = 3.

Recursion

def count_subsequences(s, t, i, j, cache):
    if j == len(t):
        return 1
    if i == len(s):
        return 0
    if (i, j) in cache:
        return cache[(i, j)]

    skip_char = count_subsequences(s, t, i + 1, j, cache)
    if s[i] == t[j]:
        use_char = count_subsequences(s, t, i + 1, j + 1, cache)
        result = use_char + skip_char
    else:
        result = skip_char

    cache[(i, j)] = result
    return result

TABLE MAPPING
Row i = how much of s we've considered (0 to len(s)).
Col j = how much of t we need to match (0 to len(t)).
table[i][j] = number of ways to form t[:j] from s[:i].

Base cases in the table:
table[i][0] = 1 for all i: empty t can always be formed (one way: pick nothing).
table[0][j] = 0 for j > 0: empty s can't form any non-empty t. 
def count_subsequences(s, t):
    rows = len(s)
    cols = len(t)
    table = [[0] * (cols + 1) for _ in range(rows + 1)]

    for i in range(rows + 1):
        table[i][0] = 1

    for i in range(1, rows + 1):
        for j in range(1, cols + 1):
            table[i][j] = table[i - 1][j]
            if s[i - 1] == t[j - 1]:
                table[i][j] += table[i - 1][j - 1]

    return table[rows][cols]

LCS vs Distinct Subsequences: same grid, different operation

LCS (parent)
Match: take it (diagonal + 1)
No match: max(skip from s, skip from t)
Goal: maximize match length
Two-sided skipping
Distinct Subsequences
Match: use + skip (diagonal + up)
No match: skip only (up)
Goal: count all paths
One-sided skipping (only from s)
Why one-sided skipping? In LCS, both strings are equal partners, so you can skip from either. In Distinct Subsequences, t is the target. You never skip characters of t (that would change what you're trying to spell). You only skip characters of s (choosing which copies to use).
Familiar pattern: this is knapsack's "grab + skip" on strings. Match = use (diagonal) + skip (up). No match = skip (up only). Count, not max. The difference from LCS: match uses ADD (count both paths), not "take the match and move on."
